# Plan: the `v0.3.0` release

Against the four issues open at `0.2.0` / spec `0.16`:
[#58](https://github.com/adamkjonsson/python-zipline/issues/58),
[#59](https://github.com/adamkjonsson/python-zipline/issues/59),
[#62](https://github.com/adamkjonsson/python-zipline/issues/62) and
[#63](https://github.com/adamkjonsson/python-zipline/issues/63). Three come from
[kober](https://github.com/adamkjonsson/kober) — a spec-driven protocol decoder —
run over real captures converted by
[zpfwire](https://github.com/adamkjonsson/python-zipline-wire); #59 is our own
debt, deferred from #55.

They are not of a kind, and the spread is the point:

| Issue | What it really is | Spec change? |
| --- | --- | --- |
| #63 | A **producer bug** in zpfwire that this library turns into a wrong number instead of a diagnostic | Yes — a missing MUST and a missing reader rule ([zipline#108](https://github.com/adamkjonsson/zipline/issues/108)) |
| #62 | A **docs bug** here, plus the read-side API that would have prevented it | Editorial only ([zipline#109](https://github.com/adamkjonsson/zipline/issues/109)); does not block |
| #59 | An **API break**, and the reason `0.3.0` is a minor | No |
| #58 | A **format gap**: a decoded record cannot say which field it is | Yes — a new Record option ([zipline#107](https://github.com/adamkjonsson/zipline/issues/107)) |

## What the research settled

Four things worth stating before the phases, because two of them contradict the
issues as filed and a third has since been overturned by a case the evidence did
not cover (Phase 6).

### 1. #63 is not a library bug first. It is a non-conformant SYN record.

The spec is explicit about the shape of a handshake record
([`zipline-payload-format.md` §Record, "Handshake records"](https://github.com/adamkjonsson/zipline/blob/v0.16/docs/zipline-payload-format.md)):

> A writer MAY record an observed TCP handshake as a zero-length record carrying
> the `syn` flag: `timestamp` is the SYN packet's capture time and **`seq_start`
> is `isn + 1`** — the stream origin, so its computed end equals it and every
> causal edge and ordering rule works unchanged.

zpfwire writes the SYN at `seq_start = isn`. That is one below the origin, and
it is the whole of the underflow. Reproduced both ways against `0.2.0`:

```
--- syn seq_start=1000 (isn=1000)  ← what zpfwire writes
record_ranges: ((4294967295, 4294967295), (0, 4), (4, 8), (8, 12))
stream_extent: 4294967295
units:         [(4294967295, 4294967295, 900), (0, 4, 1000), …]

--- syn seq_start=1001 (isn=1000)  ← what the spec says
record_ranges: ((0, 0), (0, 4), (4, 8), (8, 12))
stream_extent: 12
units:         [(0, 0, 900), (0, 4, 1000), …]
```

With a conformant SYN there is nothing wrong with `record_ranges` at all. So
the fix the issue suggests — skip zero-length records when computing the offset
— would make the symptom go away **by absorbing a malformed input silently**,
and would still leave a non-empty record below the origin wrapping to 2³²−1.
The issue anticipates this itself, under *"One thing worth deciding rather than
patching"*. We should take that branch.

**The blast radius is also wider than the issue reports.** `units()` and
`datagrams()` compute the same offset at
[`reassembly.py:566`](../src/zpf/reassembly.py#L566) and hand out
`off_start = 4294967295` per the trace above — the issue only names
`record_ranges`. Three call sites hand-roll `(seq_start - origin) % SEQ_SPACE`
([`:199`](../src/zpf/reassembly.py#L199),
[`:446`](../src/zpf/reassembly.py#L446),
[`:566`](../src/zpf/reassembly.py#L566)) and two of the three are wrong; `chunks()`
is right only by the side effect of dropping empty payloads first. That is the
real defect: **one rule, three implementations.**

### 2. The spec has no rule to appeal to, which is why we cannot just enforce it.

There is no MUST anywhere that a record's `seq_start` may not precede the
stream origin. The only MUST near it is that a TCP participant carries `isn`.
The floor is *presumed* — §"Referencing the source by stream offset" defines the
leading hole as `K = first seq_start − (isn + 1)` and says "without an `isn`
there is no room below the first captured byte" — but presumed is not stated,
and nothing tells a reader what to do with a record that sits below 0.

Consequence for us, per `CLAUDE.md`'s rule about going beyond the standard: a
check we add now enforces something `0.16` does not say. It ships **advisory,
not isolating**, and the docstring says why. See Phase 4.

### 3. #62's question already has a normative answer, and it is the expensive one.

The issue offers two readings and says the docs support both. The spec supports
only one — §Timestamp rule, on a decoded record:

> A **decoded** record inherits its `timestamp` from the data it is built from:
> the timestamp of the last source element **in its span set** — when the unit
> became complete.

Its span set, not its run. So reading 2 is normative and reading 1 is not
available without a format change nobody has asked for. Our docs are wrong in
three places and so is the canonical example
([`decoding.md:93`](../docs/user/guides/decoding.md#L93),
[`decode_stage.md:42`](../docs/user/howto/decode_stage.md#L42),
[`06_write_decoder.py:76`](../docs/user/examples/06_write_decoder.py#L76)).

**But the issue's claim that per-record times are unrecoverable is not quite
right, and the correction makes the case for an API stronger, not weaker.**
`units()` already yields per-record `(off_start, off_end, ts)` in the logical
space — the trace above shows `(0,4,1000) (4,8,2000) (8,12,3000)`. What it does
*not* do is trim overlaps the way `chunks()` does, so a hand-rolled table built
from it stamps a retransmitted range with the retransmit's time, where the spec
says the opposite:

> Under the favor-old overlap policy, a later retransmit that contributes no
> *accepted* bytes does not move `timestamp`.

So the workaround in the issue is not merely inconvenient; on a lossy capture it
is wrong. That is what earns the API in Phase 2 rather than a docs patch.

Note also that once per-payload stamps are used, the `sequenced=True`
justification at [`decoding.md:121`](../docs/user/guides/decoding.md#L121)
becomes *true* rather than needing softening. The claim was right about the
format and wrong about our own example.

### 4. `0.3.0` waits for spec `0.17`, and that is a decision rather than a finding.

#59 assumed this lands "at the same time as the 0.17 port". When this plan was
first drafted there was no 0.17 — the spec repo sat at `v0.16` with a clean tree
— and the draft argued for shipping against `0.16` and porting later, on the
grounds that everything we would propose upstream is wire-compatible and so
nothing *forces* a port.

**That is no longer the shape.** The three spec issues in Phase 5 are filed and
milestoned `0.17`, and `0.3.0` ships once they do. Two consequences, both
improvements on the decoupled version:

- **Phase 4's checks become isolating rather than advisory.** Against `0.16` a
  `seq_start` below the origin can only be *reported*, because the standard
  states no rule to enforce — `CLAUDE.md`'s "warn if the code goes beyond the
  standard". With [zipline#108](https://github.com/adamkjonsson/zipline/issues/108)
  in, it is a MUST and the checker can say so.
- **Phase 6 becomes implementable at all.** `label` cannot be emitted against a
  spec that has no such option, so the decoupled plan could only offer a
  `comment` convention. It now ships the real thing.

`SPEC_VERSION` therefore moves to `(0, 17)` and `0.3.0` is a **spec port as well
as an API break** — which the versioning rule in `CHANGELOG.md` already calls a
minor twice over. The porting checklist written for #48 gets its first real
outing; every phase below still stands, and Phase 5 moves from "propose" to
"track".

## Phase 1 — #63: one offset rule, three call sites

The root fix, not the empty-record special case.

- [ ] Add a private `_offset_of(record, origin) -> int | None` to
  [`reassembly.py`](../src/zpf/reassembly.py) — the single definition of "where
  does this record sit". It returns `None`, meaning **unplaceable**, when:
  - `seq_start is None` (the case already handled at
    [`:196`](../src/zpf/reassembly.py#L196)), or
  - `seq_start` precedes `origin` in serial arithmetic — `seq_lt` from
    [`order.py:53`](../src/zpf/order.py#L53), so wrap is handled the same way the
    ordering rules already handle it.
- [ ] Route all three sites through it:
  [`record_ranges`](../src/zpf/reassembly.py#L199),
  [`chunks`](../src/zpf/reassembly.py#L446),
  [`units`](../src/zpf/reassembly.py#L566). `chunks()`'s documented
  "zero-length records are skipped" rule stays, but stops being the only thing
  standing between a malformed input and a wrapped offset.
- [ ] Unplaceable keeps the treatment `record_ranges` already documents for a
  `seq_start`-less record: **a zero-width range at the stream's current end.**
  One range per record, in order, so the index-match against `blocks` that the
  docstring promises still holds. `units()` gains the same, where today it emits
  a wrapped offset.
- [ ] `stream_extent` needs no change — it is `max(end for …)` and inherits the
  fix. Which is the point: [`transform.py:615`](../src/zpf/transform.py#L615)
  delegates to it precisely so the coverage check cannot drift from the reader,
  and this restores that.
- [ ] Docstring on `record_ranges`: state the floor, and state that serial
  arithmetic makes "precedes the origin" undecidable beyond 2³¹ — a sequence
  that far below the origin is indistinguishable from one above it, and that is
  a property of the space, not a gap in the check.

**Tests.** Both traces above as fixtures; the conformant one is a regression
guard that the fix did not move a correct file. Add a non-empty record below the
origin, which the issue's suggested fix would not have caught. Check
`record_ranges`, `stream_extent`, `chunks`, `units` and `check_coverage` all
agree on each.

## Phase 2 — #62: make the normative timestamp reachable

The read side first, then the docs that were wrong because it was missing.

- [ ] `Segment.contributors()` → the `(off_start, off_end, ts, ts_first)`
  boundaries of the input records that make up the run, **after** the overlap
  trimming `chunks()` performs. This is the primitive; it is what a decoder
  emitting N messages from one run needs in one pass, and it is the piece that
  cannot be rebuilt correctly from outside (see finding 3).
- [ ] `Segment.ts_for(off_start, off_end)` → the completion time of a unit
  occupying that range: the `max` over contributors overlapping it. This mirrors
  the spec's "last source element in its span set" for the multi-span case, and
  it takes exactly the range the decoder is already citing, so it reads as a
  pair with `cite()`:

  ```python
  for start, end, kind in split_messages(segment.data):
      dec.record(stream, segment.data[start:end],
                 ts=segment.ts_for(start, end), cites=(start, end))
  ```
- [ ] `Segment.ts_first_for(off_start, off_end)` → the `min`, for the same
  reason `ts_first=` exists at all (#47). Cheap once `contributors()` is there,
  and it closes the same gap at the other end of the unit.
- [ ] **Derive `ts` from `cites` when it is omitted** on
  [`DecodeStage.record()`](../src/zpf/decode.py#L287). The trap in #62 is that
  the wrong answer is the easy one; this makes the right answer the default one.
  `ts=` stays available for a stage whose output has no single citable range.
  It also stops `ts` being a mandatory keyword, which helps Phase 3 a little.
- [ ] `Segment.ts` keeps its meaning — the run's completion time — and its
  docstring gains the sentence that says when it is *not* the answer.
- [ ] Fix [`decoding.md:93`](../docs/user/guides/decoding.md#L93),
  [`:318`](../docs/user/guides/decoding.md#L318),
  [`decode_stage.md:42`](../docs/user/howto/decode_stage.md#L42) and
  [`06_write_decoder.py:76`](../docs/user/examples/06_write_decoder.py#L76).
  The rule's wording at [`decode_stage.md:137`](../docs/user/howto/decode_stage.md#L137)
  is right and stays; the parenthetical at
  [`decoding.md:103`](../docs/user/guides/decoding.md#L103) that equates it with
  `Segment.ts` is the error, and goes.
- [ ] [`decoding.md:121`](../docs/user/guides/decoding.md#L121): the
  `sequenced=True` claim needs no softening once the example is fixed — say
  explicitly that it holds *because* each unit carries its own completion time,
  so the reason is on the page the next time someone reaches for `segment.ts`.

**Tests.** The three-messages-in-one-segment case from the issue, asserting
1000/2000/3000. A retransmission case, asserting the accepted bytes' time wins —
the one a hand-rolled table gets wrong. `test_tutorial_examples.py` covers the
example file already.

## Phase 3 — #59: restructure both `record()` signatures

The break that makes this a minor. Three suppressions today
([`writer.py:838`](../src/zpf/writer.py#L838),
[`decode.py:287`](../src/zpf/decode.py#L287),
[`decode.py:578`](../src/zpf/decode.py#L578)).

**Do not invent `Wire`/`Meta` bags.** The issue's own test — "a grouping earns
its place only if each group names something a producer actually thinks in" —
rules out a bag of leftovers, and there are two groupings that pass it because
the *format* already names them.

- [ ] **Reuse [`Hints`](../src/zpf/decode.py#L69) on `SessionWriter.record()`.**
  It is already `(seq_start, ack)` — literally the two options being folded, and
  the spec's own "Per Record (TCP)" table. Today the two writers spell one
  concept two ways, which is an inconsistency worth closing independently of any
  argument count. 12 → 11.
- [ ] **Add `Decoded(decoder, content_type, spans)`.** Not a bag: these three are
  exactly the options the layer rule governs — `content_type` **MUST NOT** appear
  at the transport layer, and `decoder`/`spans` are the derived-file surface. The
  grouping is the transport/decoded split the format is built on, and the spec
  states the pair as one object: `provenance = { decoder, spans }`. 11 → 9, with
  headroom for the next field the format adds.

  ```python
  session.record(alice, ts=1000, payload=b"GET /",
                 hints=zpf.Hints(seq_start=1001, ack=5001),
                 decoded=zpf.Decoded(decoder=http, content_type="mime:text/plain"))
  ```
- [ ] `DecodeStage.record()`: merge `cites` and `spans`, which are two spellings
  of one parameter (`cites` is the shorthand that fills in the ids). 11 → 10, at
  the limit. Do **not** fold `cites` into `Decoded` here — it is the hot argument
  of the hot path, and burying it would trade a lint count for real ergonomics.
- [ ] [`decode_stage()`](../src/zpf/decode.py#L578) is a *builder*, and a builder
  legitimately has knobs; it is also outside the issue's "Done when". Try folding
  `produced_by`/`produced_at` into one derived-file provenance argument — they
  are always given together and always as a pair — and if that does not read
  well, keep the suppression with a comment that says it is a builder and why
  that is different. **Decision to make; not blocking.**
- [ ] Write the exposure policy into `docs/dev/`, per the issue's "Done when":
  every Record option gets a keyword or a bundle; `extra_options` is the only
  hatch; and the rule for *where* a new option lands — transport options join
  `Hints`, decoded-layer options join `Decoded`, timing stays flat. Then fix the
  docstrings, which still claim a hatch policy that stopped being true at #55.

**Compatibility.** Clean break, no deprecation shim: `CHANGELOG.md`'s versioning
rule says every `0.x` minor is a break with no upgrade path, and a shim would
double the surface we are trying to shrink. Pay for it with a **keyword → new
form migration table** in the changelog, and file the heads-up on zpfwire and
kober before tagging, not after.

## Phase 4 — #63's other half: say it, do not just absorb it

Placing a malformed record at zero width stops the wrong number. It does not
tell anyone the file is wrong, and the file *is* wrong.

- [ ] Carry `isn` on [`_ParticipantState`](../src/zpf/conformance.py#L103) — it
  is on the Participant block and is not currently kept.
- [ ] Two checks. Both were advisory in this plan's first draft, because `0.16`
  states neither (finding 2); with
  [zipline#108](https://github.com/adamkjonsson/zipline/issues/108) landing in
  0.17 they are **isolating**, and the diagnostic cites the rule.
  - `seq-before-origin` — a record whose `seq_start` precedes `isn + 1`. Its
    bytes have no offset, so its payload is missing from every coverage answer.
  - `syn-seq-start` — a `syn`-flagged record whose `seq_start != isn + 1`, which
    is the specific shape the spec's handshake paragraph gives.
- [ ] **Write-side guard** on [`SessionWriter.record()`](../src/zpf/writer.py#L838),
  where #49's ordering guard already lives. `0.2.0` accepted `seq_start=isn` on a
  SYN record without a word; this is the fix that stops the file existing, and it
  is worth more than everything else in Phase 1 put together. Raise, do not warn:
  a producer is being told about its own output, at the moment it can still fix
  it, and the ordering guard sets that precedent.
- [ ] Note in `docs/user/errors.md` what a reader should do with a file that
  already has one — the answer is Phase 1's, and it is now sayable.
- [ ] File it against zpfwire with the two-way trace. It is a one-character fix
  there and every file it has ever written carries it.

## Phase 6 — #58: implement `label`

**Recommendation reversed from this plan's first draft.** That draft argued for
no format change, on the grounds that a `label` ships a third of a feature — name
without width or nesting — into the hottest block in the format. The four-`u32`
case is what overturned it.

**The case that decides it.** A protocol with four `u32` fields, one of them a
checksum. A consumer that wants *the checksum* must know it is the second field,
and position is not a contract — a decoder that later emits an optional field
renumbers everything after it. That case has none of the confounders the DNS
evidence carries: four siblings, contiguous, non-overlapping, every token in the
closed `prim:` vocabulary with `payload_len` binding exactly, a decoded stream
that is a well-defined 16 bytes, and a seam duty that is satisfied because the
content genuinely runs on. **The only thing missing is the name.**

So the two structural objections — nesting, and the concatenated stream — are
objections to the *bitfield* end of the spectrum, and the first draft let the
pathological case set the policy for the common one. Flat fixed-width headers are
most binary protocols.

**And the forced choice is the real defect.** `content_type = prim:u32` gives a
generic reader the value and says nothing about which field it is;
`content_type = dec:checksum` names it and destroys the normative typing, so
nothing left in the file says the four records share a type. You may have the
type or the name, never both.

**What was wrong with the first draft's reasoning**, recorded because the
argument will recur: it demanded that a `label` be *checkable* in a way `dec:`
already is not. §Typing is explicit that a `dec:` token is "a type **private to
the record's decoder**, meaning whatever that decoder documents … **name-scoped**,
not versioned" — nothing verifies it. The bar this format actually sets is a
**declared scope**, not verifiable meaning, and that is exactly what separates a
`label` from a `comment`: `comment` is documented as free text, so a consumer
parsing it relies on something the format says means nothing. The second wrong
turn was "a block, not an option" — `0x30` names a *participant*, an entity
referenced many times, whereas a field name is per-record data and an out-of-band
map forces every consumer to join two structures by offset.

- [ ] Emit and read `label` once
  [zipline#107](https://github.com/adamkjonsson/zipline/issues/107) is in 0.17:
  the block face, the JSONL face, `Record.label`, and the round-trip.
- [ ] Expose it on both writers. Per Phase 3's policy it is a decoded-layer
  option, so it joins `Decoded(...)` on `SessionWriter.record()` and is a flat
  keyword on `DecodeStage.record()`, whose whole surface is decoded.
- [ ] Conformance: **advisory**, the treatment `content_type` gets — a `label` at
  the transport layer is reported and ignored, never isolating. Dropping it loses
  nothing and the record stays readable.
- [ ] Document the convention the format deliberately does not parse: a dotted
  path, scoped to the decoder's `name`. The format sees an opaque string; the
  convention is what makes two of our own producers agree.
- [ ] Say plainly, in the same place, what `label` does **not** carry — a width
  ([zipline#105](https://github.com/adamkjonsson/zipline/issues/105)) and a
  nesting relation ([zipline#106](https://github.com/adamkjonsson/zipline/issues/106))
  — so the next producer does not read a field path as a tree the file guarantees.
- [ ] `comment` stops being the stopgap for naming and goes back to being a note.
  Worth a changelog line, since `kober` is using it that way today.

## Sequencing and risk

**Phase 5 gates the release, not the work.** Phases 1, 2 and 3 need nothing from
0.17 and can land against `0.16` while the spec issues are open; only Phase 4's
isolating checks and the whole of Phase 6 wait on a cut. Starting them now is
also how the spec issues get argued from working code rather than from a plan.

Phases 1, 2 and 4 are independent of Phase 3 and should land first: they are
fixes, and none of them touches a signature. Phase 3 is the break, so it lands
last and once, and the changelog entry is written as it lands rather than after.

The one real risk is Phase 3 against Phase 2: #62 adds a way for `ts` to be
derived at the same time #59 is reshaping the arguments around it. Doing Phase 2
first means Phase 3 reshapes a signature that already has its final parameter set
— the reverse order reshapes it twice. Phase 6 adds `label` to whatever Phase 3
settles on, so it wants the same ordering for the same reason.

`tests/vectors/` is untouched by Phases 1–4: none of them changes what a
conformant file looks like, and the `KNOWN_PASSING` ratchet in
[`test_vectors.py`](../tests/test_vectors.py) should be green at every commit.
Phase 5 re-vendors the set at `v0.17` and only ever grows that ratchet — a name
is never removed from it. `VECTOR-DEFECTS.md` defect 4 is unaffected by all of
this and stays open; nothing here should be bent to a fixture in `DEFECTIVE`.
