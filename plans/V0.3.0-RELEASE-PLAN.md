## What changed between `0.16` and `0.19`, for us

Four spec releases stand between the version this library implements and the
one it will. Everything below is what a port has to carry; the phases say where
each item lands.

### `0.17`: three things we asked for, plus `dropped`

- **`role` (`0x0092`)** on Record: a decoded record's name, independent of its
  type. Phase 6.
- **The timestamp rule is per unit, not per reassembled run**, stated outright
  at our asking ([zipline#109](https://github.com/adamkjonsson/zipline/issues/109)).
  Phase 2.
- **The handshake shape is a MUST**: a `syn` record's `seq_start` is `isn + 1`.
  Phase 4's write guard cites it.
- **`dropped`**, a fifth canonical bytes-class `reason` for content that was
  removed, and a second arm to the seam predicate
  ([zipline#98](https://github.com/adamkjonsson/zipline/issues/98)). Two vectors
  change behaviour under it and one is already in `KNOWN_PASSING`, so this is a
  breakage rather than an addition. Phase 0.

### `0.18`: corrections, one of which we depend on

- **The per-participant ordering MUST is non-descending**
  ([zipline#124](https://github.com/adamkjonsson/zipline/issues/124)). A recorded
  handshake puts the SYN and the first data record at the same `seq_start`, so a
  reader comparing with `<` rejects every real capture. We compare with
  `seq_leq` on both the checker and the sequenced-order paths already; the new
  `handshake-at-origin` vector is the regression guard. Phase 0.
- **The `syn` MUST has one strength across its whole domain**: advisory
  wherever the record sits ([zipline#116](https://github.com/adamkjonsson/zipline/issues/116),
  ours). Phase 4.
- **Content-removed is expressible only as `reason = dropped`**
  ([zipline#117](https://github.com/adamkjonsson/zipline/issues/117), ours). The
  seam predicate's second arm tests a word, and this is what makes that
  decidable. Phase 0.
- **`reject-unknown-minor` stamps a minor two ahead**: 18 at `0.17`, 20 at
  `0.19`. Phase 0.
- The re-issue moved a third of the specification into a non-normative
  companion and changed no rule. Nothing to port; it does change what our own
  docs should cite, since the argument for a rule is now in a different file
  from the rule.

### `0.19`: three packages taken, two declined

`0.19` took packages **A** (3.1, pass-through as a kind), **B** (3.2, the
sequencing basis) and **C** (3.3, pinned repairs in the advisory tier). It
declined **D** (3.4, coverage as a SHOULD) and **E** (3.5, the single axis).
That is the outcome our assessment argued for, with one refinement on C that
#65 explains and Phase 1 relies on.

**Package A.** Option `origin` (`0x0064`) is gone. Every `zpf`-sourced record
carries `spans`; a pass-through writes an **identity span** per record, the same
range in as out, and which kind a stream is, is read from the spans: identity
preserves a layer, anything else creates one. Four checker rules collapse to one
sentence, and it binds per record: a `zpf`-sourced record with no `spans` MAY be
isolated. Three vectors the analysis never listed were rebuilt on identity spans
rather than deleted: `mixed-derivation`, `isolate-self-derived` and
`chain/annotated`. **And A puts an obligation on `merge_files`** that our
assessment found and priced as conditional on D, which then did not land: a
merge output now cites its input streams, so it is answerable for their coverage,
and a transport input's holes are real ranges no payload covers. Phase 3.

**Package B.** Options `sequenced_basis` (`0x0053`) and File Header `flags`
(`0x0014`, whose only bit was `SINGLE_CLOCK`) are gone, with the soundness rule,
the recording rule and the reader-side rule on unrecognised values. `SEQUENCED`
is a bare assertion. The forensic question moved to build provenance:
`produced_by`, `produced_at` and `transform_params_digest` on the file that set
the flag. Phase 0.

**Package C, as refined.** The origin floor is no longer a MUST NOT. A record
below the origin, or one with no `seq_start` on a stream whose other records
carry one, is **unplaceable**: it covers no byte of the stream and contributes
nothing to the extent, whatever range a reader reports for it, and a reader
accepts the file and SHOULD report the record. What `0.19` dropped is only the
pinned range. So #63's disagreement between our reader and kober's is licensed
at the range level and closed at the extent level, which is the level that
matters. Phases 1 and 4.

**The vector inventory**, from #65. Removed (9): `advisory-below-origin-payload`,
`advisory-seq-start-below-origin`, `annotator-decoded`, `file-clock-metadata`,
`isolate-sequenced-no-basis`, `partially-hinted-sequenced`,
`passthrough-discontinuity`, `passthrough-transport`, `sequenced-basis`. Added
(3): `sequenced-session`, `unplaceable-below-origin`, `unplaceable-no-seq-start`.
Together with `0.17` and `0.18`'s additions, the suite is at 53 names over 59
files, and against **our** `0.16` vendoring the delta is seven names out and
seven in. Phase 0 has the arithmetic.

### What #64 said back about our assessment

Three points, recorded because they shape decisions below.

- **The `0.18` re-issue added a Goals entry**, *make a decoding failure
  findable in the input's own bytes*, and it is what settled D against the clean
  SHOULD. The coverage MUST, `input_extents`, `reason_class`, the seam predicate
  and `check_extents` all **stay**. Every item the old plan had for them stays
  with them.
- **Transforming decoders are a gap in our assessment.** We have no decoder
  that changes data, so we could not price what D or E would do to decryption
  or decompression. It bore only on D and E and both were declined, so nothing
  here turns on it — but it is a gap in this library's coverage of the format
  worth remembering when kober reaches TLS.
- **Line count is the wrong yardstick**, and the spec repository has stopped
  using it. Ranking the five by whether the rules they delete serve a stated
  goal put B and C first, A mixed, D and E last. `0.19` took exactly the first
  three.

## What the research settled

Three findings from the earlier drafts still hold and are kept in brief; the
fourth is superseded by the section above.

### 1. #63 is a non-conformant SYN, and the fix is one offset rule

zpfwire writes the SYN at `seq_start = isn`, one below the origin, and that is
the whole of the underflow. Reproduced both ways against `0.2.0`:

```
--- syn seq_start=1000 (isn=1000)  ← what zpfwire writes
record_ranges: ((4294967295, 4294967295), (0, 4), (4, 8), (8, 12))
stream_extent: 4294967295

--- syn seq_start=1001 (isn=1000)  ← what the spec says
record_ranges: ((0, 0), (0, 4), (4, 8), (8, 12))
stream_extent: 12
```

The blast radius is wider than the issue reports: `units()` and `datagrams()`
compute the same offset at [`reassembly.py:566`](../src/zpf/reassembly.py#L566),
and three call sites hand-roll `(seq_start - origin) % SEQ_SPACE`
([`:199`](../src/zpf/reassembly.py#L199), [`:446`](../src/zpf/reassembly.py#L446),
[`:566`](../src/zpf/reassembly.py#L566)). **One rule, three implementations** is
the defect, and it survives every spec version: under `0.19` the record is
unplaceable rather than non-conformant, but a reader still has to place it
somewhere, and ours places it near 2³².

### 2. #62's question has a normative answer, and it is the expensive one

A decoded record's `timestamp` is that of the last source element **in its span
set**, per unit and not per run. Our docs are wrong in three places and so is
the canonical example. And `units()` does not trim overlaps the way `chunks()`
does, so a hand-rolled per-unit table stamps a retransmitted range with the
retransmit's time, where the spec says the opposite. That is what earns the API
in Phase 2 rather than a docs patch.

### 3. `role` is the right shape, and `comment` was never it

The four-`u32` case decides it: a consumer wanting *the checksum* must know
which field it is, position is not a contract, and `content_type` can carry the
type or the name but never both. `role` is scoped to the decoder's `name` like a
`dec:` token, asserts no tree and no width, and is opaque to the format. Phase 6
is unchanged from the previous draft except that its one caveat is closed:
`advisory-transport-role` now exists
([zipline#118](https://github.com/adamkjonsson/zipline/issues/118)).

### The terminology sweep

`0.19` pinned three words, and our docstrings use the old ones. A **decoder** is
an identity, not a stage. A **transform** is only the file → file stage.
**Recode** is coined for changing bytes without adding structure, and reassembly
is a decoder because it recodes.

- [x] Sweep `decode.py`, `transform.py`, `writer.py` and `docs/user/guides/decoding.md`
  for "decoder" used to mean a stage, and for "transform" used for the
  byte-changing act. `transform.py`'s module name is correct under the new
  definition. Low priority, and can trail the release.

## Phase 1 — #63: one offset rule, three call sites — **DONE** (2026-09-06)

The root fix, not the empty-record special case. Unchanged in mechanics from
the old plan; changed in what the spec says about it.

> One box below stays open on purpose: the **report** an unplaceable record is
> owed needs the checker to know the origin, which is Phase 4's work, and the
> question of where that report lives is the open decision recorded there.
> This phase stops the wrong number and nothing more.

- [x] Add a private `_offset_of(record, origin) -> int | None` to
  [`reassembly.py`](../src/zpf/reassembly.py), the single definition of "where
  does this record sit". It returns `None`, meaning **unplaceable**, when
  `seq_start is None` on a sequence-anchored stream, or when `seq_start`
  precedes `origin` in serial arithmetic (`seq_lt` from
  [`order.py:53`](../src/zpf/order.py#L53)).
- [x] Route all three sites through it: `record_ranges`, `chunks`, `units`.
- [x] **The placement is now ours to choose**, and we keep the running maximum
  `0.18` pinned: a zero-width range at the highest `off_end` any earlier record
  of the participant reached, `0` where there is none. It is what
  `record_ranges` already does for a `seq_start`-less record. Say in the
  docstring that the range is unpinned by the specification since `0.19`, that
  two readers may differ on it, and that every extent agrees regardless because
  the record covers no byte. That last clause is the rule; the range is a
  convenience.
- [x] `stream_extent` needs no change and inherits the fix, which is the point:
  [`transform.py:615`](../src/zpf/transform.py#L615) delegates to it so the
  coverage check cannot drift from the reader.
- [x] **A reader SHOULD report an unplaceable record**, and it is not a
  violation, so it does not belong to the `nonconformant` category. Decision:
  route it through the checker's advisory path anyway — the block is kept, the
  reader records a diagnostic, a checking writer refuses it — but give the
  `Diagnostic` its own category, `unplaceable`, so a consumer can tell "this
  file is wrong" from "this record has no offset". **Landed in Phase 4, and not
  through the advisory path**: that would have made a checking writer refuse a
  block the format permits, so the checker gained a third channel and the
  reader a list of its own. Doing that needs the checker
  to know the origin, which is Phase 4's `isn` on `_ParticipantState`; so the
  report lands with Phase 4 and this phase only stops the wrong number.

**Tests.** Both traces above as fixtures; the conformant one is a regression
guard. A non-empty record below the origin, which the issue's suggested fix
would not have caught. Check `record_ranges`, `stream_extent`, `chunks`,
`units` and `check_coverage` all agree on each.

**And this phase is where `unplaceable-below-origin` turns green.** It did,
as an `XPASS`, the moment the rule landed — `_EXTENTS_PENDING` is now empty.
The table was worth its keep exactly as argued: the vector passed the tier
tests throughout, and nothing but the extents assertion ever said it was
passing for the wrong reason.

### What Phase 1 execution changed

- **The fixtures use the flat writer, not `zpf.create`.** Phase 4 adds a
  write-side guard that refuses a below-origin record, so building these files
  with the checked writer would have made this phase's own tests fail two
  phases later. `malformed()` in
  [`test_reassembly.py`](../tests/test_reassembly.py) uses `BlockWriter`, which
  is also the honest way to say what these files are: output no producer should
  have written, which a reader meets anyway.
- **`chunks` and `units` skip an unplaceable record where `record_ranges`
  gives it a zero-width range**, and the asymmetry is deliberate rather than an
  oversight. `record_ranges` promises one range per record, index-matched to
  `blocks`, so it must return something. A :class:`~zpf.Datagram` promises its
  `data` occupies `[off_start, off_end)`, and a zero-width one carrying eight
  bytes would be a lie in the data structure. The record stays reachable
  through `session.stream(pid)` either way, so nothing vanishes — which is what
  the specification means by "zero width is not deletion".
- **The below-origin test is undecidable past 2³¹**, and the docstring says so.
  Serial arithmetic cannot tell a sequence far below the origin from one far
  above it, so a stream carrying more than 2 GiB in one direction reads its own
  later records as below-origin. That is the space, not a gap in the check, and
  the alternative is trusting the wrapped offset.
- **A test the plan did not ask for, and the one that justifies the placement.**
  Records within a participant may overlap, so the record stored last is not
  always the one that reached furthest — a retransmit ending lower than its
  predecessor. `test_the_unplaceable_range_is_the_running_maximum_not_the_last_end`
  is what makes the running maximum a decision rather than an accident, and it
  is the argument `0.18` used when the placement was still mandatory.

### What Phase 2 execution changed

## Phase 4 — #63's other half: say it, do not just absorb it — **DONE** (2026-09-06)

Placing an unplaceable record stops the wrong number. It does not tell anyone,
and the spec now says a reader SHOULD. **This closes #63.**

- [x] Carry `isn` on [`_ParticipantState`](../src/zpf/conformance.py#L103).
- [x] **`syn-seq-start`, advisory in both directions.** A `syn`-flagged record
  whose `seq_start != isn + 1` violates a MUST, and `0.18` gave the whole MUST
  one strength: accept, report. `0.19` kept that sentence. This is the one
  check from the old Phase 4 that survives as a *conformance* finding.
- [x] **`seq-before-origin` is not a violation any more.** It becomes an
  `unplaceable` *report* rather than a finding: `0.19` withdrew the MUST NOT
  and kept only the effect, and a reader SHOULD report the record.

  **Decision to make, and it is not a category question.** Both vectors sit on
  the accept tier with `violations: 0` and neither is marked advisory, so
  `test_accept` asserts `reader.diagnostics == []`. Diagnostics are one flat
  list, so **any** entry fails that assertion whatever its `category` — the
  earlier draft of this plan said "not a `nonconformant` diagnostic", which
  does not help. Reporting and passing are mutually exclusive as the reader is
  built today. Three ways out:

  1. **A separate accessor** — `FileReader.unplaceable`, a list of
     `(session_id, pid, index)` or of `Diagnostic`, populated alongside but not
     inside `diagnostics`. Satisfies the SHOULD, keeps the vectors green, and
     says in the API what the format says: this is not a violation.
     **Recommended**, and it costs one attribute.
  2. **Do not report.** Cheapest, and defensible since the spec says SHOULD.
     But #63 exists because a malformed file produced a silently wrong number,
     and silence is what we are fixing.
  3. **Report into `diagnostics` and special-case the harness.** Rejected:
     it makes our vector harness disagree with the manifest, and the manifest
     is the acceptance criterion.

  **Settled as option 1**, on the plan's own reasoning that it is correct under
  either answer upstream gives. `FileReader.unplaceable` is a list of
  `Diagnostic` under a category of its own, populated beside `diagnostics` and
  never inside it.

  **Upstream has been asked to settle it**, as the second half of
  [zipline#140](https://github.com/adamkjonsson/zipline/issues/140): the
  manifest can say *clean* and *breaks a rule and is reported*, but not *breaks
  no rule and is still reported*, which is the state `0.19` created. An answer
  either gives the vectors a field saying a report is owed, in which case
  option 1 is right and the harness asserts it, or says silence is conformant
  on a `violations: 0` vector, in which case option 2 is defensible. Do not
  block on it: option 1 is correct under both answers, and only the harness
  assertion changes.
- [x] **Write-side guard** on [`SessionWriter.record()`](../src/zpf/writer.py#L838),
  where #49's ordering guard lives. Two cases, and they differ in standing:
  - A `syn` record not at `isn + 1`: **raise**. It is a MUST on the writer, and
    a producer is being told about its own output at the moment it can fix it.
  - A payload-carrying record below the origin: **raise, and say this is
    stricter than the standard.** `0.19` permits the file; its bytes are simply
    in no offset, excluded from the extent and every coverage answer. No
    producer wants that, the only known instance was a bug, and the standard's
    own words are "the price of not trusting the wrapped offset". Per
    `CLAUDE.md`, the docstring and `errors.md` carry the callout that this
    refusal goes beyond the standard, and why.
- [x] `docs/user/errors.md`: what a reader does with a file that already has
  one. The answer is Phase 1's, and the category is `unplaceable`.
- [x] File the SYN off-by-one against zpfwire with the two-way trace, if #63's
  thread has not already. It is a one-character fix there and every file it
  has ever written carries it.

- [x] `comment` goes back to being a note. Changelog line, since kober uses it

### What Phase 6 execution changed

- **`role` put `DecodeStage.record()` back over the argument limit**, so
  `src/zpf/` carries **two** `# noqa: PLR0913`, not the one Phase 5 left. The
  policy written in Phase 5 already had the exception that covers it, and now
  says so outright: every record a decode stage writes is decoded-layer, so a
  `decoded=` wrapper would appear on every call and distinguish nothing. A
  bundle that is *always* present is ceremony rather than structure — the
  opposite of what `Decoded` buys on `SessionWriter.record()`, where it marks
  the line between a record that speaks to the decoded layer and one that does
  not. The builder's comment claimed to be the only suppression and was
  corrected with it.
- **One check, not two.** The plan said the two labels "should share their
  implementation"; `_transport_content_type` became `_transport_label` and
  reports both in one message, which the advisory tier already supports. A
  check per label would be two places to update when the format adds a third.
- **Nothing to do for the pass-through carry-forward, and something to do for
  the filter.** The plan predicted this: our only pass-through is the merge,
  whose input is transport. `rewrite_decoded` is what re-emits decoded records,
  and it now copies `role` beside `content_type`. Because the option is
  advisory, no reader could detect a stage that dropped it — which is why that
  needed a test rather than a checker.
- **The vectors went green in two steps**, and the order is worth noting. The
  block and JSONL faces alone took `decoded-field-roles` and both round-trip
  cases; `advisory-transport-role` needed the conformance check as well. So the
  suite distinguished "we can carry the option" from "we apply the rule about
  it", which is what a separate vector for the advisory strength is for.

## Sequencing and risk

**Phase 0 went first, and is done.** It removed three options and four checker
rules, which was new ground: nothing had ever been *removed* in a port before.
The order held — B, then A, then `dropped`, then the re-vendor and the ratchet
— with one departure. Package A could not leave the merge for Phase 3, because
deleting `Origin` breaks it in the same commit; see §What Phase 0 execution
changed.

**Every phase has landed, in the order this section set.** Ordering the fixes
ahead of the break paid as intended: `record()` was reshaped once, against a
parameter set that had stopped moving, and `ts` had already stopped being a
required keyword by the time the count mattered. Phase 6 landed last on the
settled signature, as planned — though it did add a parameter, which is what
put the decode stage back over the limit. Phase 3 landed with them rather than being carried:
two of its three items were statements that had become false, and the third was
repairing a parameter Phase 0 left inert. Phase 5 is the break, so it lands last
and once; Phase 6 lands on whatever Phase 5 settles.

**The one real risk is discharged.** It was Phase 5 against Phase 2 — that
reshaping `record()` before #62 added its parameter would reshape it twice.
Phase 2 landed first, so `DecodeStage.record` has its final parameter set and
Phase 5 reshapes it once. Note that `ts` is no longer a required keyword there,
which takes the signature a little of the way on its own.

**What the ratchet does at each step.** Phase 0 landed it at **52**, not the 55
this plan projected — three vectors went to `DEFECTIVE` on upstream defects we
found while porting. From here every commit is green, with four names held:
`decoded-field-roles` and
`advisory-transport-role` until Phase 6, and `handshake-at-origin`,
`unplaceable-below-origin` and `mixed-derivation` until
[zipline#141](https://github.com/adamkjonsson/zipline/issues/141) is fixed —
that last one is held on its `tcp_role` defect alone now, its extent being
correct since Phase 1. So the set reaches **55** at Phase 6 and **58** only if
upstream fixes the fixtures.

Phases 2 through 5 change no conformant file's shape. Phase 1's external guard
was the `_ACCEPT_EXTENTS` table, which is why Phase 0 added it and held the
vector out; it went green as an `XPASS` and `_EXTENTS_PENDING` is now empty.
Phase 3's items had no vector either, so `test_transform.py` is their only
guard — which is why the pass-through coverage claim was run rather than
asserted.
