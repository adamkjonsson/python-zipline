# Plan: the `v0.8.0` release

> Written 2026-10-29 against `0.7.0` (spec `0.23`), from the seven issues on the
> [`0.8.0` milestone](https://github.com/adamkjonsson/python-zipline/milestones).
> Phases 0–7 done 2026-10-29: the `0.24` port is implemented, every vector
> passes, writing a record costs 45% less, and the distribution is
> `python-zipline`. Phase 8 (downstream) next.

## The theme: the `0.24` port, and two things a port is the right time for

The `0.7.0` plan closed by warning that
[zipline#166](https://github.com/adamkjonsson/zipline/issues/166) "remains the
thing that would reshape `0.8.0`". It did: spec
[`0.24`](https://github.com/adamkjonsson/zipline/releases/tag/v0.24), *the
sessionizer release*, was tagged on 2026-10-29. It closed #166 and five other
issues, and it took all six findings of our review
([`SPEC-0.24-REVIEW.md`](SPEC-0.24-REVIEW.md), PR #103). So `0.8.0` is a port
first. Five of the seven issues are the port.

The other two are not spec work, and both belong in a release that breaks
anyway:

- **#102, the distribution name.** Renaming what `pip` installs breaks every
  dependency string downstream. Doing it in the release that also moves the
  version gate costs downstream one migration instead of two.
- **#101, the write path's per-record cost.** It is behaviour-preserving, so it
  could ship any time. But #106 adds per-record work to that same path (the
  `copy` checks), so measuring #101 after #106 lands is the only measurement
  that describes what ships.

## Decisions for the maintainer

Each had a proposed default, so the work was not blocked on it. *D1–D4
decided 2026-10-29, each as proposed. D5 is decided in Phase 6, by design.*

- **D1, #102: the distribution name.** **Decided: `python-zipline`.** It
  matches the repository, and `pypi.org/pypi/python-zipline/json` returns 404
  (checked 2026-10-29). The import name stays `zpf`. Two cautions:
  - A 404 is not a reservation. PyPI also refuses names it judges too similar
    to existing ones, so the name is only safe once registered. Registering it
    is outward-facing, so it is the maintainer's step.
  - `zipline` on PyPI is the unrelated Quantopian backtester, which `CLAUDE.md`
    already notes. `python-zipline` sits next to it in search results. The
    alternative `zipline-payload` (also 404) names the format rather than the
    repository and avoids that confusion.
- **D2, #106: the "messages as sent" affordance.** **Decided as proposed:** a `copy: bool`
  attribute on `Datagram`, plus `StreamView.datagrams(copies=True)`, where
  `False` skips flagged records. The default keeps what the capture saw, which
  is what `datagrams()` returns today. The spec states both readings, so
  either default is within the standard.
- **D3, #106: the checker's category for a broken `copy`.** **Decided as proposed:** a
  semantic violation that isolates the session, under a new category
  `copy-mismatch`. That is the spec's licence, and `isolate-copy-differs`
  expects it.
- **D4, #107: a named convenience for the incomplete-reassembly block.**
  **Decided: yes**, `SessionizeStage.incomplete(cites, *, comment)`, writing
  `reason="undecodable"`. It is two lines over `undecoded()`, and it makes the
  pinned word the default instead of something to remember.
- **D5, #101 item 4: a write-side `check=False`.** **Decided 2026-10-29:
  taken at the end of Phase 6, with its measurements**, not in advance.
  - *Against it:* items 1–3 make the same checks cheaper and write the same
    bytes, but item 4 drops the checks. On the read side, #97's `check=False`
    changes what is *reported* about a file that exists. On the write side it
    would change what is *produced*: the writer refusing a violation before
    writing any bytes is how the library keeps to the standard. #101 leaves
    that design question open, and zpfwire, which filed it, would not want it
    as the default.
  - *For it:* the checker is about 21% of a record's write time at `0.7.0`
    (9.8 µs → 7.7 µs with it stubbed out). Items 1–3 shrink everything else,
    so its share grows afterwards, and Phase 5 adds the `copy` checks to the
    same path.
  - *No deadline:* a keyword-only `check=False` is additive, so any later
    minor can add it. Nothing about `0.8.0` being a breaking release makes it
    cheaper now.

  So: if items 1–3 bring the cost down enough, item 4 is not needed. If the
  checker then dominates, there is a measured case to weigh against the lost
  guarantee.

## Phase 2: #104, the FIN's position

First of the normative phases, because it is the one where this library
currently writes output that its own checker rejects.

**Done 2026-10-29.** 1,261 passed, 1 xfailed (`isolate-copy-differs`, #106),
`ruff` and the docs build clean. `decoded-past-fin/decoded` joined
`KNOWN_PASSING`.

- [x] **One definition of reach.** `stream_extent` was **already right**: it
      takes the furthest `record_ranges` end, and a zero-length placeable
      record ranges `(off, off)`. Only the view drifted. `StreamView.chunks()`
      skipped zero-length records before they could move its cursor, so the
      memo recorded the last byte's end. It now tracks reach separately.
      Both docstrings say that reach is not `_sequence_end`'s *end*, and so
      does `CLAUDE.md`'s offsets trap.
- [x] **One definition of a FIN's position**, `fin_positions()` in
      `reassembly.py`, exported beside `stream_extent`. It shares
      `record_ranges`' origin rule through a new `_transport_origin`, and
      skips unplaceable records, which `record_ranges` gives a zero-width
      range they must not be mistaken for. `StreamView.fin_positions()`
      returns the same positions from the same walk, now a three-part memo.
- [x] **More than the plan said: a lost tail is now a hole.** Once a pure ACK
      reaches past the last byte, the range up to it is a hole, the
      rationale's own case (*data [0,100), lost [100,150), ACK at 150*). So
      `chunks()` yields a trailing `Gap`, minus the FIN's position, which
      `0.7.0`'s comment said "cannot occur". Auto-fill marks it `gap`.
- [x] **`check_coverage`** exempts the positions `fin_positions` finds in the
      input, for the gap test only. A lost FIN stays a one-wide hole.
- [x] **Auto-fill** (the ledger's `autofill`) leaves the FIN's position
      unmarked, for both stages.
- [x] **Not in the plan: the single-file check.** The first failure on
      `decoded-past-fin/decoded` was the reader's `extent-exceeds-coverage`,
      not `check_coverage`. A derived file alone cannot see a FIN, and the
      position is always the stream's last offset, so a one-wide shortfall
      at the tail is undecidable from one file. `extent-exceeds-coverage`
      now fires on a shortfall of **more than one**, in the reader, the
      writer and `check_extents`, and `check_coverage` decides the last
      position. Documented as a blind spot in `docs/dev/conformance.md`
      (*What one file cannot decide*), in both error tables, and in the
      checker's docstring. **Reported upstream as
      [zipline#174](https://github.com/adamkjonsson/zipline/issues/174)**: the
      spec's `input_extents` paragraph still calls the guarantee
      self-verifiable from the file alone, which since #168 holds to within
      one position. It suggests one sentence, and a two-wide negative vector
      to pin that the tolerance stops at one.
- [x] **Tests**:
  - 7 in `test_reassembly.py`, each measured three ways (cold, warm and from
    the blocks): a pure ACK past the FIN, a FIN with nothing past it, a
    zero-length FIN's reach against its end, a zero-length FIN with an ACK
    past it, a lost FIN, a lost tail, and a decoded stream;
  - 4 in `test_decode.py`: the #104 repro over `closed-final-ack` (8 and 5,
    no Undecoded, both checks clean), auto-fill leaving the position alone,
    a lost FIN filled `gap`, and `check_coverage` exempting a FIN but not a
    lost one;
  - 1 in `test_conformance.py`: one wide is accepted, two wide is not.

  **Each was checked to bite**, by breaking one rule at a time from a backup:
  the view's zero-length reach (4 failures), the FIN exemption in the
  trailing hole (2), auto-fill's exemption (2), `check_coverage`'s (4,
  including the new accept pair), and the single-file tolerance (3, including
  `test_accept[decoded-past-fin/decoded]`).
- [x] **Changelog *Changed*, observable**, plus *Added* for the two
      `fin_positions`. Phase 8 measures the byte change downstream.

**Two things the rebuild found**, neither a bug in this phase's code:

- **The fragment vectors stamp a reassembled record with its first packet's
  time.** `sessionized-fragments` stamps its datagram 1000, the first
  fragment's, where the spec's timestamp rule says *the packet time of the
  **last** packet that contributed bytes*, which is 1200.
  `sessionized-across-break` does the same (1000, not 1300), and so did
  `0.22`'s `sessionized-across-units`; the upstream plan says the new
  vectors copied that one. The rule carries no keyword and readers MUST NOT
  reject over timestamps, so the files are still accept-tier, but they teach
  the stamp the rule forbids. This stage derives 1200, with `ts_first` 1000,
  and the rebuild test compares everything but times. **Recorded as defect 8**
  in `VECTOR-DEFECTS.md` and reported as
  [zipline#175](https://github.com/adamkjonsson/zipline/issues/175). It holds
  nothing out, so `DEFECTIVE` stays empty.
- **`SessionizeStage.session()` always writes its flow key** as the Session's
  `key` option, and the fragment vectors write none. `key` is optional, so
  both files conform, but a caller cannot reproduce a key-less session.
  Noted, not changed: the key is what the stage's own flow table uses.

## Phase 5: #106, `copy`'s semantics

The bit and token landed in Phase 1. This is the rest.

**Done 2026-10-29.** **1,278 passed and nothing xfails**: every `v0.24` case
is in `KNOWN_PASSING`, `isolate-copy-differs` the last to join. `ruff` and the
docs build clean.

- [x] **Writer and checker are one implementation.** The rules live in
      `ConformanceChecker._check_copy`, which every block written passes
      through, so the writer refuses and the reader isolates from the same
      code. That is how every other semantic rule here works, and two copies
      could drift. The rules:
  - the payload must equal the participant's preceding record's, and there
    must be one;
  - no `copy` on a stream whose records carry `seq_start`. That is caught at
    the copy when `seq_start` came first, and at the participant's close when
    it comes after, since only then is the stream known to be anchored.

  Bits are tested with `int` arithmetic, which is #101's item 2.
- [x] **Two deviations from this plan, both deliberate:**
  - **A reference, not a digest.** The plan said to keep a digest of the last
    payload. That hashes *every* record's payload on the off chance the next
    is a copy, which is the per-record cost #101 is about. Holding a
    reference to the previous payload bytes costs nothing per record, compares
    only when a `copy` arrives, and holds one payload per participant until
    Session End, which is less than a digest table would.
  - **D3's category name.** D3 said *isolate the session, as
    `copy-mismatch`*. The reader reports every semantic violation under the
    one category `nonconformant` and isolates the **block**, the smallest
    unit, as the spec's tier allows; a named category would have needed new
    plumbing for one rule. So the message names the rule (*…flagged copy, but
    its payload differs from its participant's preceding record's…*), which is
    what `_ISOLATE_REASONS` matches, and the record dropped is exactly the one
    whose claim is false.
- [x] **Checker scope**: transport-layer records only. On a decoded record the
      flag is preserved, never checked or interpreted, as the spec says.
- [x] **Reader**: D2's `Datagram.copy` (a dataclass field with a `False`
      default, set by the view from the stream's layer, so it is never true on
      a decoded record) and `StreamView.datagrams(copies=True)`. `concepts.md`
      names both readings as the specification's.
- [x] **Transforms**: confirmed and documented. `merge_files` keeps every
      record of each participant in order, so a predecessor is never lost.
      `rewrite_decoded` reads decoded layers only, where the flag is opaque.
- [x] **Tests**:
  - 8 in `test_conformance.py`: a copy and a copy of a copy, a differing
    copy, a first-record copy, a copy after the *peer's* record (accepted),
    a copy after another of its own participant's messages (isolated, the
    spec's own edge), all three `seq_start` orders, a decoded record
    unchecked, and the writer refusing then accepting;
  - 2 in `test_reassembly.py`: `udp-capture-copy` read both ways, with
    offsets and extent 58 unchanged, and a decoded record never read as a
    copy.

  **Each was checked to bite.** One check at first did not: with the
  record-time `seq_start` test removed, a copy after a `seq_start` record was
  still caught, but at the participant's close, so the test passed. It now
  requires the mid-stream catch, which is the one that isolates the record
  itself, and it fails when the check is removed.
- [x] **README** restored to *every one of them passing* and *complete 0.24
      support*, both true from this phase on; Phase 9's step for it is done
      early. `CLAUDE.md` says the port is implemented.
- [ ] **Watch** [zipline#171](https://github.com/adamkjonsson/zipline/issues/171)
      (what `copy` means on a decoded record). Nothing here depends on it.

## Phase 6: #101, the write path

After Phase 5, so the per-record cost it measures includes the `copy` checks.

**Items 1–3 done 2026-10-29: 11.1 → 6.05 µs a record at 64 B (−45%), and
11.5 → 6.3 at 1,460 B, with no byte moved.** 1,293 passed, `ruff` and the
docs build clean.

- [x] **Pin the bytes first**: `tests/test_write_bytes.py` writes two files
      (TCP with every hint, SYN/FIN, pure ACKs, comments and a UDP copy; and a
      derived file with spans, content types and roles), checks both are
      conformant, and compares SHA-256 with digests taken at `5aa1e67`, before
      any change. Not one moved across the three items. It was seen to fail
      with two options swapped.
- [x] **Baseline**, with the issue's harness: a script kept outside the repo
      that writes 60,000 transport records with `seq_start`/`ack`, a
      `Decoded`, `PSH`, and `ts_first` every other record, and takes the median
      of three. Every row of the table below is that script.
- [x] **Item 2**, integer flag tests: `_SYN_BIT`, `_FIN_BIT`, `_MESSAGE_BIT`
      and `_COPY_BIT` in `blocks.py`, and all ten flag tests in `src/zpf/`
      switched to `int(flags) & _X_BIT`. That includes Phase 5's `_check_copy`,
      written `int(flags) & RecordFlags.COPY`, which still goes through `enum`
      because the right operand is a Flag. That form was a trap and the
      comment beside the constants names it.
- [x] **Item 1**, `Record._encode` as a fixed encoder: fixed-width options
      packed header and value together by one `struct` each (`_OPT_U32`,
      `_OPT_I64`, `_OPT_U16`), in the spec table's order, which the docstring
      lists. **Guarded twice:** the byte pin, and
      `test_the_fixed_record_encoder_matches_the_spec_walk_on_every_vector`
      in `test_blocks.py`, which encodes all 185 vendored Records both ways,
      plus one Record with every option, an unknown extra and spans past one
      TLV's cap. Both fail with two options swapped.
- [x] **Item 3, not as the plan worded it.** *Skip re-validating inputs the
      writer already checked* does not hold: `ts`, `flags`, `payload` and the
      hints reach `Record` straight from the caller, unchecked. So validation
      stays, and gets cheaper: one chained range test over every field, with
      the ten per-field checks only when it fails or cannot compare, so a bad
      value raises exactly what it did. The type normalisation is skipped
      where the type already matches (re-wrapping a `RecordFlags` ran `enum`).
      Ten new tests pin each field's error and the normalisation, which no
      test did before.
