# Plan: the `v0.6.0` release

> Written 2026-09-27 against `0.5.0` (spec `0.21`), from the three issues on
> the [`0.6.0` milestone](https://github.com/adamkjonsson/python-zipline/milestone/4):
> [#75](https://github.com/adamkjonsson/python-zipline/issues/75),
> [#76](https://github.com/adamkjonsson/python-zipline/issues/76) and
> [#77](https://github.com/adamkjonsson/python-zipline/issues/77).
>
> **Status: not started.** No branch, no code. `main` is at `5b26440`, clean.

## The finding this plan turns on

The three issues are not one release. They differ on the only axis that
decides a release here — *does the spec move?* — and two of them are gated on
things outside this repository.

| Issue | What it is | Spec change? | Blocked on | Natural release |
| --- | --- | --- | --- | --- |
| [#77](https://github.com/adamkjonsson/python-zipline/issues/77) | `decode_stage` cannot pass `params_digest` — an **additive keyword**, ~10 lines | No | Nothing | **`0.5.1`**, now |
| [#75](https://github.com/adamkjonsson/python-zipline/issues/75) | The ack comparison is serial against a stale anchor — a **rule change** | **Yes**, and it is not ours to make | [zipline#151](https://github.com/adamkjonsson/zipline/issues/151), open, no reply | `0.6.0`, *if* `0.22` is cut |
| [#76](https://github.com/adamkjonsson/python-zipline/issues/76) | No fan-out sessionization stage — a **new builder** | No | Nothing | `0.6.0` |

Three consequences, in the order they bite:

1. **#77 should not wait for `0.6.0`.** It is additive, it is small, and the
   issue says plainly that it fits a `0.5.x` and that kober would pin
   `>=0.5.1,<0.6`. Holding it inside a minor that is gated on an unanswered
   spec question blocks kober `0.5.0` on a spec release it has no stake in.
   Cut `0.5.1` first. This plan's Phase 1 is that release.
2. **`0.6.0` is, in substance, the `0.22` port.** #75's fix is "whatever
   #151 settles on", and #151's candidate — acks unwrap along the acker's
   stored order — changes *what a reader computes*. That is exactly what
   `0.21` did on the offset axis, and `0.21` was a full spec minor. By the
   rule in `docs/dev/contributing.md` § *Porting to a new spec version*, a
   spec minor is always a library minor: the gate moves, `0.5.x` files stop
   being readable, and the vectors are re-vendored. So closing #75 is not a
   patch to `order.py`; it is a port, and the port is what makes `0.6.0` a
   minor.
3. **#76 rides along but does not depend on it.** It is pure library work,
   touches none of the ordering code, and would be a minor on its own only
   because it is large. It is the release's headline feature either way.

### The decision this plan cannot make

**Is spec `0.22` being cut, and when?** `zipline#151` is open with no
response and no `0.22` tag exists; the spec repository's last commit is the
`0.21` plan closing. The spec is yours, so this is a scheduling choice, not
a dependency to wait on — but `0.6.0` cannot close #75 until it is made.

- **If `0.22` is cut** — `0.6.0` = the port (#75) + fan-out (#76). Phases 2–7
  below, in order.
- **If `0.22` slips** — ship `0.6.0` as **fan-out only** (#76 + the `0.5.1`
  content), move #75 to a `0.7.0` milestone, and say in its thread that the
  library tracks #151 rather than pre-empting it. `0.6.0` is still a minor:
  #76's API surface is new, and there is no reason to hold a finished
  feature for an unfinished rule.

**Recommendation: plan for the port, but do not block on it.** Start #76
immediately — it is the long pole, ~2–3× the port's code, and independent of
everything else. Revisit the branch at the point #76 is review-ready; if
`0.22` is not tagged by then, take the fan-out-only release and let #75 move.

Everything below is written for the first branch. Phases marked **[0.22]**
drop with the port; the rest ship regardless.

## Phase 3 — **[0.22]** the ack unwrap (#75)

The rule, as #151 proposes it: acks unwrap along the **acker's** stored
order by signed serial delta, anchored at the first ack's delta from the
**peer's** origin; the comparison becomes integer `>=` against the record's
unwrapped end, which `record_ranges` already computes.

Sites, and one the issue does not name:

- [ ] `_check_not_already_acked` / `_StoredOrder`
      ([`order.py:344`](../src/zpf/order.py), [`order.py:246`](../src/zpf/order.py)).
      `_max_ack` becomes an unwrapped position. **Watch the streaming
      contract**: `_StoredOrder` is O(1) per participant and never buffers —
      that is what lets the writer's linearize guard share it — and the
      anchor it now needs (the peer's origin) must be reachable without
      buffering. The writer knows `isn` at participant declaration; the
      reader-side `verify_sequenced` takes only records, so decide whether
      the anchor comes from the first ack observed or is passed in, and keep
      both callers on one implementation.
- [ ] `_Placer` in `reassembly.py` is the single definition of the offset
      walk and the checker and writer guard already share it. Reuse it or
      state why the ack walk cannot; **do not grow a second unwrapping
      rule** — `CLAUDE.md` names the single definition on purpose.
- [ ] **`_pair_ready` in `causal_merge`** ([`order.py:158`](../src/zpf/order.py))
      makes the *same* serial comparison — `seq_lt(head.ack,
      record_end(peer_head...))` — between an ack and a peer record end, and
      #75 does not mention it. It is step 2 of the merge algorithm, which is
      the rule #151 is actually about, so it is in scope for this phase.
      **Not demonstrated to fail**: probing it at `0.5.0` produced no false
      stall, because a frontier that is not ready is merely deferred while
      the peer is ready, so the effect would be a *mis-ordering* rather than
      a refusal, and no shape in hand produces one. Audit it against the
      settled rule, and record the answer either way — a comment saying why
      the merge is safe is worth as much as a fix.
- [ ] The vector #151 asks for (*a stream past 2 GiB, sequenced, with a peer
      that only acks*) should exist upstream. If `0.22` ships without it,
      file for it and carry the shape as a local regression test meanwhile,
      clearly marked as ours and not a vector.
- [ ] Re-run #75's repro verbatim; it must write and verify clean, and the
      `stream-past-2gib` and `sequenced-session` vectors must not move.
- [ ] Tell python-zipline-wire: its `0.4.0` carries this as a strict `xfail`
      and a documented limit naming #75. The `xfail` becomes an
      `xpass` — they need the heads-up before the tag, not after.

## Phase 4 — fan-out sessionization (#76)

The long pole, and independent of Phases 2–3. The issue has the analysis;
the plan here is the order of work.

- [ ] **Decide the shape first**: a new `sessionize_stage` builder, or a mode
      of `decode_stage`. The issue sketches the former and leaves it open.
      Weigh it against `DecodeStage`'s existing 1:1 `output_layer=TRANSPORT`
      path, which must keep working either way — two builders sharing an
      accounting core is likely cleaner than one builder with two mapping
      modes, but that is the call to make and record here.
- [ ] `FileWriter.derive_from` grows a no-mirror mode, or the stage declares
      its `zpf-input` Source directly and skips it.
- [ ] Output sessions and participants created **on demand** with fresh ids,
      cached per flow key; `record` targets an output session while citing an
      input stream — the two decouple.
- [ ] Coverage accounting per **input** stream across **all** output
      sessions: `_cited`/`_marked` are already keyed by input
      `(session_id, pid)`, so the change is that auto-fill takes the union
      across output sessions before filling.
- [ ] `Session End`: each output session declares the **whole** extent of
      every input stream it cited — *under fan-out a consuming session
      declares the whole input stream, not its share*. `_declare_extents`
      currently groups by output `session_id` matching the input's, which is
      exactly the assumption that breaks.
- [ ] Seams: a transport-layer output is **forbidden** a Discontinuity (its
      offsets carry the hole), so `joins_previous` does not apply — but an
      input break must not be crossed by an output record. `DecodeStage`
      already declines the crossing at 1:1; preserve that.
- [ ] **Acceptance, from the issue**: rebuild `tunnel/inner.zpf` from
      `tunnel/packets.zpf` through the new API and match the vendored file —
      byte-for-byte, or semantically with a stated reason for any block-order
      difference. Write the rebuild to a tmp path and compare; **never write
      into `tests/vectors/`**, which is vendored verbatim.
- [ ] Docs: a guide section for the fan-out case (the decrypted-tunnel
      pipeline is the worked example, and `docs/user/` has the decode-stage
      guide to hang it off), and `decode_stage`'s `output_layer=TRANSPORT`
      text says plainly that it is the 1:1 case and points at the new entry
      point.
