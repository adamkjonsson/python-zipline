# Plan: the `v0.6.0` release

> Written 2026-09-27 against `0.5.0` (spec `0.21`); **revised 2026-10-13**
> against `0.5.1`, from the three issues now on the
> [`0.6.0` milestone](https://github.com/adamkjonsson/python-zipline/milestone/4):
> [#75](https://github.com/adamkjonsson/python-zipline/issues/75),
> [#76](https://github.com/adamkjonsson/python-zipline/issues/76) and
> [#79](https://github.com/adamkjonsson/python-zipline/issues/79).
>
> **Status: Phase 1 shipped as `0.5.1`; Phase 1b (#79) verified by kober and
> released as `0.5.2` on 2026-10-13. `0.6.0` is on hold until spec `0.23`**
> (decided 2026-10-13), so the decision below is made: `0.6.0` waits for the
> spec and will be a port, not a fan-out-only release.

## What changed since the first draft

- **#77 shipped as `0.5.1`** on 2026-09-27, as this plan recommended. Phase 1
  is kept below as a record.
- **#79 joined the milestone.** It has #77's shape exactly: an additive
  keyword on the decode-stage wrapper, blocking kober, with the issue itself
  suggesting a `0.5.x`.
- **Upstream has not moved.** [zipline#151](https://github.com/adamkjonsson/zipline/issues/151)
  is open with no reply since 2026-09-19. The spec repository's last commit
  is still the `0.21` plan closing (2026-09-18), and no `v0.22` tag exists.

## The finding this plan turns on

The same as before. The three issues are not one release, and the axis that
splits them is still *does the spec move?*

| Issue | What it is | Spec change? | Blocked on | Natural release |
| --- | --- | --- | --- | --- |
| [#79](https://github.com/adamkjonsson/python-zipline/issues/79) | `DecodeStage.undecoded` cannot pass `reason_class`. An **additive keyword**, plus the phantom-mark fix below | No | Nothing | **`0.5.2`**, now |
| [#75](https://github.com/adamkjonsson/python-zipline/issues/75) | The ack comparison is serial against a stale anchor. A **rule change** | **Yes**, and not ours to make | [zipline#151](https://github.com/adamkjonsson/zipline/issues/151), open, no reply in 3½ weeks | `0.6.0` *if* `0.22` is cut, else `0.7.0` |
| [#76](https://github.com/adamkjonsson/python-zipline/issues/76) | No fan-out sessionization stage. A **new builder** | No | Nothing | `0.6.0` |

1. **#79 should not wait for `0.6.0`**, for the reasons #77 did not: it is
   small and additive, and kober's `fails_as` cannot write a
   `decrypt-failed` region through the stage without it. Going around the
   stage to `stage.writer.undecoded` corrupts coverage accounting, so there
   is no workaround. Cut **`0.5.2`** first (Phase 1b).
2. **`0.6.0` is the `0.22` port only if `0.22` exists.** #75's fix changes
   what a reader computes, which by `docs/dev/contributing.md` § *Porting to
   a new spec version* is a spec minor and so a library minor.
3. **#76 is the headline and the long pole either way.** It touches none of
   the ordering code.

### The decision this plan cannot make

**Is spec `0.22` being cut, and when?** The spec is yours, so this is a
scheduling choice, not a dependency to wait on.

- **If `0.22` is cut**, `0.6.0` = the port (#75) + fan-out (#76).
- **If `0.22` slips**, `0.6.0` = **fan-out only**. Move #75 to a new `0.7.0`
  milestone and say in its thread that the library tracks #151 rather than
  pre-empting it.

**Recommendation: start #76 now, and decide at the point it is
review-ready. Default to fan-out-only.** In the first draft the two branches
were even. After 3½ weeks with no movement on #151 they are not: unless
`0.22` work has *started* upstream by the time #76 is ready, ship without it.
Holding a finished builder for an unanswered rule question helps no one, and
python-zipline-wire already carries #75 as a strict `xfail`, so nothing
downstream is broken in the meantime.

Phases marked **[0.22]** drop out on the fan-out-only branch.

## Phase 1b: `0.5.2`, `reason_class` on `DecodeStage.undecoded` (#79)

A patch release on its own branch, tagged before any `0.6.0` work merges.

- [x] **The keyword.** Add `reason_class: str | None = None` to
      `DecodeStage.undecoded` ([`decode.py:458`](../src/zpf/decode.py)) and
      pass it to `Writer.undecoded` ([`writer.py:660`](../src/zpf/writer.py)),
      which already takes it. **Do not validate in the stage.** The writer's
      checker owns the canonical table (`blocks.py:51`) and the
      class-disagreement rule (`conformance.py:733`), and a second copy
      would drift. The docstring says when the keyword is required and
      points at the canonical four, as `Writer.undecoded`'s does.
- [x] **Phantom marks: the bug found while planning this.** `undecoded()`
      appends to `_marked` *before* calling the writer
      ([`decode.py:483–487`](../src/zpf/decode.py)), and `record()` does
      the same with `_cited` ([`decode.py:395–401`](../src/zpf/decode.py)).
      If the writer refuses the block and the caller catches the error and
      carries on, the stage has already counted the bytes as covered.
      `_autofill` then skips them, and the stage **closes cleanly and writes
      a file that fails the coverage guarantee** the stage exists to
      provide. Reproduced at `0.5.1` against `tunnel/packets.zpf`: catch
      #79's `SemanticError`, let the stage close, and
      `check_coverage(out, packets)` reports `coverage-gap … [0, 4) is
      neither decoded nor marked Undecoded`. The fix is to track only after
      the write returns, in both methods. #79 makes this more reachable:
      catching a refused reason and retrying with a class is exactly what a
      caller learning the keyword will do.
- [x] **Tests, from the issue,** through `decode_stage`:
      - `reason="decrypt-failed", reason_class="bytes"` writes, and the
        output passes conformance and `check_coverage`.
      - The same reason without a class still raises the `SemanticError`.
      - `reason="gap", reason_class="bytes"` raises the checker's
        disagreement error.
      - A custom hole-class reason (`reason_class="hole"`) over an input
        break is accepted and is not re-filled by `_autofill`.
- [x] **Tests for the phantom-mark fix:** a refused `undecoded()` and a
      refused `record()`, each caught, then the stage closes and
      `check_coverage` is clean, with the refused range auto-filled.
- [x] `CHANGELOG.md` `0.5.2`: *Added* (the keyword) and *Fixed* (phantom
      marks). Quality gate; tag `v0.5.2`.
- [ ] Tell kober the pin is available (`>=0.5.2,<0.6`).

Acceptance: kober can write a `decrypt-failed` region through the stage, and
the output passes `check_coverage` whether or not the caller ever caught a
refusal along the way.

## Phase 3: **[0.22]** the ack unwrap (#75)

The rule as #151 proposes it: acks unwrap along the **acker's** stored order
by signed serial delta, anchored at the first ack's delta from the **peer's**
origin. The comparison becomes integer `>=` against the record's unwrapped
end, which `record_ranges` already computes.

- [ ] `_check_not_already_acked` / `_StoredOrder`
      ([`order.py:344`](../src/zpf/order.py), [`order.py:246`](../src/zpf/order.py)).
      `_max_ack` becomes an unwrapped position. **Keep the streaming
      contract:** `_StoredOrder` is O(1) per participant and never buffers,
      which is what lets the writer's linearize guard share it. Decide where
      the anchor (the peer's origin) comes from without buffering, and keep
      both callers on one implementation.
- [ ] Reuse `_Placer` (`reassembly.py`) or state why the ack walk cannot.
      **Do not grow a second unwrapping rule**; `CLAUDE.md` names the single
      definition on purpose.
- [ ] **`_pair_ready` in `causal_merge`** ([`order.py:158`](../src/zpf/order.py))
      makes the same serial ack-vs-record-end comparison, and #75 does not
      name it. This has not been shown to fail: at `0.5.0` an unready
      frontier was merely deferred, so the effect would be a mis-ordering,
      not a refusal. Audit it against the settled rule and record the
      answer either way.
- [ ] The vector #151 asks for (a stream past 2 GiB, sequenced, with a
      pure-ACK peer) should exist upstream. If `0.22` ships without it, file
      for it and carry the shape as a local regression test marked as ours.
- [ ] Re-run #75's repro verbatim. It must write and verify clean, and
      `stream-past-2gib` and `sequenced-session` must not move.
- [ ] Tell python-zipline-wire **before** the tag: their strict `xfail`
      becomes an `xpass`.

## Phase 4: fan-out sessionization (#76)

The long pole, and independent of Phases 2–3. The issue has the analysis;
this is the order of work.

- [ ] **Decide the shape first**: a new `sessionize_stage` builder, or a mode
      of `decode_stage`. The 1:1 `output_layer=TRANSPORT` path must keep
      working either way. Two builders over a shared accounting core is
      likely cleaner than one builder with two mapping modes; make the call
      and record it here.
- [ ] **Extract the accounting core before building on it.** `_cited`,
      `_marked`, `_track`, `_autofill` and the seam check move into
      something both builders own. Do this **after** `0.5.2` merges, so the
      phantom-mark fix and #79's keyword are in the core from the start and
      the fan-out stage's `undecoded` takes `reason_class` without a second
      patch. Fan-out stages are where `decrypt-failed`-style reasons will
      come from.
- [ ] `FileWriter.derive_from` grows a no-mirror mode, or the stage declares
      its `zpf-input` Source directly.
- [ ] Output sessions and participants are created **on demand** with fresh
      ids, cached per flow key. `record` targets an output session while
      citing an input stream.
- [ ] Coverage per **input** stream across **all** output sessions:
      auto-fill takes the union of citations before filling.
- [ ] `Session End`: each output session declares the **whole** extent of
      every input stream it cited. `_declare_extents` groups by matching
      `session_id`, which is exactly the assumption that breaks.
- [ ] Seams: a transport-layer output is forbidden a Discontinuity, but an
      input break (packets.zpf has one at offset 100) must not be crossed by
      an output record. Preserve `DecodeStage`'s refusal.
- [ ] **Acceptance, from the issue:** rebuild `tunnel/inner.zpf` from
      `tunnel/packets.zpf` through the new API and match the vendored file,
      byte-for-byte or semantically with a stated reason for any block-order
      difference. Write to a tmp path; **never write into `tests/vectors/`**.
- [ ] Docs: a fan-out section in the decode-stage guide with the
      decrypted-tunnel pipeline as the worked example. `decode_stage`'s
      `output_layer=TRANSPORT` text says plainly that it is the 1:1 case and
      points at the new entry point.
