# Plan: the `v0.2.0` milestone

Against issues [#47](https://github.com/adamkjonsson/python-zipline/issues/47),
[#48](https://github.com/adamkjonsson/python-zipline/issues/48) and
[#49](https://github.com/adamkjonsson/python-zipline/issues/49), all raised by
[zpfwire](https://github.com/adamkjonsson/python-zipline-wire) — a capture →
`.zpf` converter with TCP reassembly — against library `0.1.0` / spec `0.16`.
Plus [#50](https://github.com/adamkjonsson/python-zipline/issues/50), split out
of #49 during this plan (Phase 3c) and since added to the milestone: **four
issues, not three.**

They are not of a kind. #48 is half-done and its remainder is a process change;
#47 is a keyword argument and an afternoon; #49 is a design question with a
wrong premise in it; #50 is the largest, and carries the milestone's only
unsettled design question.

---

## What the research settled

Three things worth stating before the phases, because two of them contradict
the issues as filed.

**#49's premise about write-time enforcement is half right, and the half that
is wrong is the half that matters.** The issue says "the ordering MUST is
enforced per participant at write time, so a producer has to get the
interleaving right before the first `record()` call". The *per-participant*
part is true: [`_check_record_order`](../src/zpf/conformance.py#L794) runs on
every Record, sequenced or not, and `FileWriter` feeds the checker inline at
[`writer.py:601`](../src/zpf/writer.py#L601), so a participant's `seq_start`
values must be non-decreasing as they are written. The *interleaving* part is
not: the cross-participant ack rule — a record must not appear after a peer
record that already acknowledged its bytes — is explicitly **not** checked,
and [`conformance.py:50`](../src/zpf/conformance.py#L50) says so in as many
words ("out of single-pass reach ... needs the merge algorithm").

The consequence is a real gap, and it is worse than the issue supposes: a
producer can set `sequenced=True`, emit a badly interleaved session, and get a
silently non-conformant file with no error from this library at any point.
`verify_sequenced` exists and would catch it, but nothing calls it on the write
path. That gap, not the buffering helper, is the most valuable thing in #49.

**#49 asks for something DECODER_API item 6 does not cover.** Item 6
([`DECODER_API.md`](DECODER_API.md), line 402) is about the **decode stage**:
ordering *decoded* records by the input's `timeline()`, and a `sequenced=` whose
verification is "the emitted timestamps are non-decreasing", because decoded
records are hint-less. zpfwire is doing the opposite — emitting **capture-sourced
transport-layer** records for a TCP session, which are hint-*ful*, carry seq/ack,
and are ordered by causal edges rather than by timestamps. Filing this under
item 6 conflates them. They share `causal_merge` and nothing else, and the plan
below splits them.

**No spec-bump checklist exists** anywhere in the repo — not in
`docs/dev/contributing.md`, not in `CLAUDE.md`, not as a template in `plans/`.
Each migration plan grew its own phase list ad hoc. So #48's second half is
writing one that does not exist, not amending one that does.

## Phase 2 — #47, `ts_first=` on the ergonomic writer

The narrowest of the three, and the issue's reasoning is sound: the field
exists on [`Record`](../src/zpf/blocks.py#L1108), both faces handle it
([`jsonl.py:490`](../src/zpf/jsonl.py#L490) and the `_SPEC` table), and only
the ergonomic writer omits it — so a capture-sourced producer must drop to
`write_block` and hand-manage the ids `SessionWriter` exists to manage.

The issue's argument for *why* is the load-bearing part and it holds: a
capture-sourced file cannot carry `spans` at all (every span must reference a
`zpf-input` source, [`conformance.py:790`](../src/zpf/conformance.py#L790)), so
for a pcap → zpf tool `ts_first` is the only way to record when a coalesced
record started.

- [ ] Add `ts_first: int | None = None` to
  [`SessionWriter.record()`](../src/zpf/writer.py#L699), keyword-only, passed
  straight through to the `Record` it builds. No validation beyond what
  `Record.__post_init__` already does (`_check_i64_opt`).
- [ ] Remove `ts_first` from the two "rare options without a keyword here"
  notes, at [`writer.py:20`](../src/zpf/writer.py#L20) and
  [`writer.py:730`](../src/zpf/writer.py#L730). Both still list `comment` and
  `extra_options`, which stay true.
- [ ] Test: round-trip a record written through `SessionWriter.record(...,
  ts_first=...)` and read the field back; assert the binary and JSONL faces
  agree. `tests/test_writer.py` already writes a `ts_first` via `write_block`
  at line 225 — extend from there.
- [ ] Docs: the writer how-to and API reference.

**Two decisions to take explicitly, not by default:**

1. **Do we validate `ts_first <= timestamp`?** The spec fixes `timestamp` as
   the last contributing packet and `ts_first` as the first, so a file with
   `ts_first > timestamp` is nonsense — but the specification states no such
   rule and the checker enforces none. Rejecting it would be **going beyond the
   standard**, which `CLAUDE.md` requires be called out rather than done
   quietly. Recommendation: **do not** add it to `ConformanceChecker`. If it is
   wanted, it belongs in the advisory tier that `0.16` introduced, which
   accepts-and-reports rather than rejects. That is a separate issue, not this
   one.
2. **Does `DecodeStage.record()` get `ts_first=` too?** It has the same gap
   ([`decode.py:275`](../src/zpf/decode.py#L275)). Recommendation: **not in
   this issue.** For a decoded record the "first contributing packet" is a
   question about the input's provenance, which decoded records answer with
   `spans` — the exact thing a capture-sourced record cannot do and the reason
   `ts_first` exists. Adding it there needs its own argument.

## Phase 3 — #49, split in two

The issue asks two questions and offers to contribute. Both deserve answers
before any code, because the answer to the first changes what gets built.

### The answers

**Q1 — is there an intended writer-side helper?** There is not, today, and the
expectation the issue offers as the fallback ("a producer drives `causal_merge`
itself and passes `sequenced=True`") is what the library currently supports —
but it is unguarded in the way described above. So: **yes, there should be a
helper, and its most important job is verification, not buffering.** A producer
that already has the whole session in memory can call `causal_merge` in three
lines; what it cannot do is find out that it got it wrong.

**Q2 — for a hint-ful session, is `sequenced_basis` genuinely expected to be
absent?** Yes, and the reading is right.
[`_check_sequenced_basis`](../src/zpf/conformance.py#L464) requires it only
when `sequenced and not has_hints`, where `has_hints` is set by any record
carrying `seq_start` or `ack`. A TCP session is hint-ful, its order rests on
causal edges the file itself records, and the basis is therefore not required.
It is also **not forbidden** — setting it on a hint-ful session is accepted
today, and nothing in `0.16` makes it a violation. `verify_sequenced` is
indeed the right check for the hint-ful case.

### 3a — the write-side guard (the part zpfwire needs)

- [ ] Add an opt-in `verify=True` to `begin_session(sequenced=True)`, or a
  `SessionWriter.sequenced_guard()` — naming to settle in review. It maintains
  the `verify_sequenced` state incrementally as records are written: `last_seq`
  and `max_ack` per participant, O(1) per participant, no buffering. This is
  the same single-pass shape the checker already uses; the reason
  `ConformanceChecker` cannot host it is that it must not raise on files it
  merely *reads*, and the ack rule is a stored-order rule the format permits a
  reader to trust rather than re-derive.
- [ ] Raise at the offending `record()` call, naming both records — the
  producer's own frame, not a post-hoc file error.
- [ ] Decide whether this is opt-in or on-by-default for `sequenced=True`
  sessions. Recommendation: **on by default**, off by an explicit escape
  hatch. Asserting SEQUENCED and getting it wrong produces a file that readers
  will trust and mis-order, and the cost is two ints per participant.

### 3b — a producer-side linearizer

- [ ] `zpf.linearize(streams)` or `SessionWriter.write_sequenced(streams)`:
  buffer a session's per-participant records, run `causal_merge`, emit in the
  resulting order, set the flag. Thin — `causal_merge` already does the work
  and is already streaming — but it is the piece that turns "get the
  interleaving right before the first `record()` call" into one call.
- [ ] Document the memory characteristic honestly: `causal_merge` holds one
  frontier record per participant, but a *producer* feeding it from live
  reassembly holds whatever it has not yet emitted. This is a buffer-and-emit
  helper, not a streaming one, and the docstring should say so.

### 3c — item 6 proper, and what to do with it

Item 6 as written is the **decode-stage** feature: order decoded records by the
input's [`timeline()`](../src/zpf/reader.py#L324), then opt-in `sequenced=`
verified by non-decreasing timestamps. It is a different feature from 3a/3b and
zpfwire does not need it.

- [x] **Split it out of #49** into its own issue, leaving #49 to be the
  hint-ful producer story it actually describes — #49 retitled to match. Done:
  [#50](https://github.com/adamkjonsson/python-zipline/issues/50), **on the
  `v0.2.0` milestone**. Item 6 stays unchecked on the `DECODER_API.md`
  checklist until it lands.
- [ ] **Settle what `sequenced_basis` a decoded stage writes.** Decoded output
  ordered by the input's timeline is hint-*less*, so the basis is a MUST — but
  it rests on the input file, which is not obviously any of `clock` /
  `protocol` / `external` / `trivial`. This is the one open design question in
  the milestone, and it **gates only the `sequenced=` half** of #50: the flag
  cannot be set until it is answered. Timeline ordering has no such dependency
  and can land alone, so if the basis question proves hard, split #50 on that
  line rather than slipping both.
- [ ] Note that item 6 carries an explicit warning worth preserving: *"**Do
  not** carry `seq_start` onto decoded records to work around the skewed-clock
  case without an explicit decision — it goes beyond the standard."*

## Sequencing

Phases 1 and 2 are independent of each other and of 3, and both are small;
either can land first. Phase 3a is the design-risk item in #49 and is the one
to review before writing. 3b depends on nothing but is only worth doing once
3a settles the naming.

3c is no longer only triage. With #50 on the milestone it is real work, and it
is the critical path: the largest of the four, dependent on item 3 (shipped),
and holding the only unsettled design question. Answer the `sequenced_basis`
question first — it gates half of #50, and answering it early is what makes
the ordering/`sequenced=` split a live option rather than a rescue.

Nothing here changes the on-disk format, the version gate, or any conformance
rule — with the single exception flagged in Phase 2 decision 1, which the
recommendation declines. So `KNOWN_PASSING` should not move, and if it does,
something is wrong.

- `ts_first=` on `DecodeStage.record()` (Phase 2, decision 2).
