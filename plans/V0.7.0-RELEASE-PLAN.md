# Plan: the `v0.7.0` release

> Written 2026-10-23 against `0.6.0` (spec `0.23`), from the five issues on the
> [`0.7.0` milestone](https://github.com/adamkjonsson/python-zipline/milestone/6).
>
> **Status: not started.** `main` is at `5f6e81b`; `src/` and `docs/` are
> identical to the `v0.6.0` tag.

## The theme: streamability and cost

`0.6.0` was the second spec port in a row, and both ports were judged on
correctness. This release is the first in a while that is **not** a port, and
it takes the question the ports deferred: the format's goals promise
*append-only / streamable […] bounded memory on unbounded input*, and three of
the five issues are places this library does not deliver that. One issue
(#87) is unrelated and is what makes the release a minor.

Measured at `0.6.0`, 64-byte payloads, `tracemalloc` peak:

| Path | Now | After |
| --- | --- | --- |
| Write capture-sourced, 100k records | 0.1 MB | unchanged ✅ |
| Write **derived** (spans), 100k records | **13.7 MB** | ~0.1 MB (#96) |
| `open()` binary, 100k records | 4.9 MB | ~4.9 MB (structure is the design) |
| `open()` derived, 100k records | 20.1 MB | ~5 MB (#96) |
| `open()` JSONL, 50k records | 19.2 MB | unchanged — documented instead (#98) |
| `open()` CPU | — | ~30% faster with `check=False` (#97) |

**What is not in scope.** The reader's index is *meant* to be eager in
structure — it is what buys independent per-session iterators and O(1)
random access, and `ranges`/`layers` are documented caches. Making
`zpf.open` streaming is not on the table; #98 instead makes the guide say
what it actually is, and points at `BlockReader`/`JsonlReader` for callers
who need bounded memory. Nor is the JSONL face's eagerness a bug: a text
stream cannot be seeked back to a block.

## The issues

| Issue | What it is | Risk | Why this release |
| --- | --- | --- | --- |
| [#96](https://github.com/adamkjonsson/python-zipline/issues/96) | Coverage ledgers keep one interval per span, never coalesced | **Low** — behaviour-preserving | The writer's streaming break; biggest win per unit of risk |
| [#93](https://github.com/adamkjonsson/python-zipline/issues/93) | `SessionReader.layer()` materialises a whole participant; 3–4 parse passes per input | Low / **Medium** | The memory fault is a bug; the pass removal is not |
| [#97](https://github.com/adamkjonsson/python-zipline/issues/97) | No way to open without the checker (~30% of the pass) | Medium — new API | Needs the minor |
| [#87](https://github.com/adamkjonsson/python-zipline/issues/87) | Derive `ts_first` in `DecodeStage.record` | Low, but **observable** | **The reason this is a minor** |
| [#98](https://github.com/adamkjonsson/python-zipline/issues/98) | The reading guide promises flat memory | None — docs | Needs Phases 1–3 to have landed before it can state the right numbers |

## Phase 1 — #96: coalesce the coverage ledgers

The release's centre, and the one to land first: it changes no verdict, and
every later phase measures against it.

**Done 2026-10-23.** Measured against the plan's own table: the derived write
peaks at **0.2 MB** where it was 13.7, `open()` on a derived file at **4.9 MB**
where it was 20.1 — the same figure as a capture-sourced file of that size, so
the span term is gone rather than reduced. 100k records citing one identical
range cost **0.15 MB**, from 7.3.

- [x] `add(into, start, end)` and `coalesce(intervals)` in
      [`_intervals.py`](../src/zpf/_intervals.py), which is already the single
      home for this arithmetic. `add` is the incremental one and is what the
      ledgers call; it has an O(1) fast path for the in-order case and bisects
      only when a range arrives out of order.
- [x] `_StreamLedger.spans`/`.undecoded` ([`conformance.py:222`](../src/zpf/conformance.py))
      are coalesced on insert. **The flag this plan called for was not needed**:
      coalescing never empties a non-empty set, so the existing emptiness test
      still answers *did any record cite this stream?* — the worry was
      unfounded, and a flag would have been state with nothing to say.
- [x] The stages' `_Ledger._cited`/`_marked` ([`decode.py:202`](../src/zpf/decode.py))
      the same way, kept apart, with a comment at `autofill` saying why.
- [x] Drop the now-redundant `sorted()` calls at `covered` and in `autofill`.
- [x] **Acceptance, as tests rather than a script** — `tests/test_memory.py`.
      A script in the repo is a script nobody runs; these are three
      assertions, deliberately loose (a growth *ratio*, not a byte figure, so
      they do not fail on an interpreter change). Verified they bite: patching
      the coalescing back out makes the ratio 8.1× and leaves 1,000 ranges in
      the ledger, and both tests fail.
- [x] Property tests in `tests/test_intervals.py`, where Hypothesis found one
      thing worth keeping: `complement` does not tolerate a *reversed* range
      where `coalesce` drops it. Both ledgers filter `start < end` before
      inserting, so it cannot arise — the strategy says so rather than the
      property pretending the two agree on input neither sees.
- [x] `KNOWN_PASSING` stays full and no vector's verdict moves. 1,145 tests
      green, no expectation edited.

One observable change, in the changelog: where auto-fill reports a range both
cited and explicitly marked, the message can now name the whole clash where it
used to name its first fragment. The raise, and the offsets it covers, are
unchanged.

## Phase 2 — #93: the reader's passes

Two halves, deliberately separated because only one is safe.

**Done 2026-10-23.** Taking one unit from a 20,000-record unit sequence falls
from **22.4 MB to 1.1 MB**; a decode stage over the same input drops from five
parse passes to four.

- [x] **The memory fault** ([`reader.py:319`](../src/zpf/reader.py)):
      `stream_layer(list(self.stream(pid)), ...)` materialised every record of
      a participant to keep one answer. `stream_layer` iterates its argument
      once, so the parameter widened from `Sequence` to `Iterable` and the
      generator is passed through — same eager semantics, same error timing,
      O(1) memory. A changelog *Changed* line, since `zpf.stream_layer` is
      public; widening an input type breaks no caller.
- [x] **The extent pass** ([`decode.py:306`](../src/zpf/decode.py)) — **not
      by the route this plan proposed.** Accumulating it in `_SessionIndex`
      during indexing would have put a second copy of the placement walk in
      the reader, and the index is where Phase 1 had just finished *removing*
      per-record state. Instead the walk the caller already makes records the
      two numbers as it goes: `chunks()` and `units()` set them on
      exhaustion, and `StreamView.extent_and_gaps()` reuses them or walks if
      nothing has. Generator semantics do the hard part — the recording line
      sits after the loop, so only a complete walk sets anything and an
      abandoned one cannot leave a partial measurement behind.

      `_extent_and_gaps` in `decode.py` is gone; the view measures itself,
      which is also where the memo belongs. `test_sessionize.py`'s #91
      guarantee (*an input stream is measured once under fan-out*) moved to
      the new seam rather than being dropped.
- [x] **Did not** take the issue's third option (resolve the layer from the
      first record carrying a `decoder_id`, validate the rest lazily). It
      moves when a mixed-layer participant raises, from `layer()` to
      mid-iteration, and both the checker and `strict` reading lean on that
      timing. The conservative fix got the memory without touching it, so the
      question never had to be opened.
- [x] Corrected the issue's arithmetic: pass 2 fires **only** for an
      `adjacency = units` participant, because `is_unit_sequence`
      short-circuits on the byte before consulting the layer
      ([`reassembly.py`](../src/zpf/reassembly.py)). The measured 4.00× is
      real but specific to the field-granular input it was measured on; an
      ordinary transport input paid 3, and now pays 2.
- [x] Agreement tests in `tests/test_reassembly.py`: the cold walk and the
      memo must give one answer, over a contiguous stream, an interior hole, a
      leading hole, a packet-oriented stream, an empty stream, an abandoned
      walk, and a **trailing Discontinuity** — the last cross-checked against
      `zpf.stream_extent`, the independent definition it must not drift from.
      Verified it bites: recording the walk's cursor instead of the last
      record's end fails it.

**One pass is still unaccounted for.** The stage now makes two record passes
where the caller needs one: its own read, and the `layer()` resolution behind
`is_unit_sequence`. That is #93's direction (1) in its stronger form, and it
is the option deliberately left open above — so the remaining pass is the
price of the error timing, not an oversight. Worth a line in the issue when it
is closed.

## Phase 3 — #97: `check=` on the reader

**Done 2026-10-23.** Measured over 60,000 records: `open()` goes from
**0.465 s to 0.328 s**, a 30% saving — the figure the profile predicted.

- [x] `zpf.open(..., check=True)` / `FileReader(check=…)`; `False` skips the
      per-block `_admit` call and the end-of-stream `finish()`.
- [x] `strict=True, check=False` raises `ValueError` — strict mode's entire
      content is *raise on what the checker found*.
- [x] `_check_self_derivation` stays on regardless: it is a path comparison on
      the Source table, costs nothing per block, and is the one rule whose
      violation makes spans resolve against the wrong file.
- [x] Structural diagnostics (truncation, trailing bytes) still arrive — they
      come from `BlockReader`/`JsonlReader`, not the checker. Tested, along
      with `diagnostics`/`unplaceable` carrying no `"nonconformant"` entries
      with the checker off, and a malformed frame still raising.
- [x] Docs: the option in the reading guide and a *Declining the checker*
      section in [robustness](../docs/user/howto/robustness.md), each saying
      what is given up and framing it as *for a file this process wrote*,
      not *for speed*.

**The option found a bug, which is the phase's real result.** `check=False`
is meant to change what is *reported*, not what is *read* — but
`_file_into_index` looked each block's session up directly, relying on the
checker having isolated any block naming one the file never declared. With
the checker declined, such a record raised `KeyError` straight out of
`zpf.open`. It is dropped from the index now, which is exactly what
isolation did, so the index is the same either way and no checked read
changes. The test that caught it was written to assert the *reported*
difference on the suite's existing nonconformant fixture; it failed on the
crash instead.

One API reference in this phase's first draft — `zpf.check_conformance` —
does not exist; it is `zpf.ConformanceChecker`. Caught by checking the
export list rather than by the docs build, which would not have flagged the
prose copy.

## The risk this plan carries

The same one the `0.6.0` plan carried, and it is worth naming rather than
discovering: **[zipline#166](https://github.com/adamkjonsson/zipline/issues/166)
is open and `spec`-labelled.** A fragmented datagram over a `units` input has
no conformant record, because `0.22`'s permission is keyed on `seq_start`; the
preferred option extends that permission to fragment reassembly, which lands in
`_check_cites` in [`sessionize.py`](../src/zpf/sessionize.py) — the stage
`0.6.0` shipped. If that becomes `0.24`, it arrives as a port and swallows this
release the way `0.22`/`0.23` reshaped the `0.6.0` plan.

**Do not wait for it.** Every issue here is independent of the spec, four of
the five are small, and holding finished work behind an unanswered spec
question is the mistake #77 nearly made. If `0.24` is cut mid-flight, the port
becomes Phase 0 of a replan and these phases renumber behind it — which is
exactly what the `0.6.0` plan did, and it survived the move.
