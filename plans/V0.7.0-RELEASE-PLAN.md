# Plan: the `v0.7.0` release

> Written 2026-10-23 against `0.6.0` (spec `0.23`), from the five issues on the
> [`0.7.0` milestone](https://github.com/adamkjonsson/python-zipline/milestone/6).
>
> **Status: not started.** `main` is at `5f6e81b`; `src/` and `docs/` are
> identical to the `v0.6.0` tag.

## The theme: streamability and cost

`0.6.0` was the second spec port in a row, and both ports were judged on
correctness. This release is the first in a while that is **not** a port, and
it takes the question the ports deferred: the format's goals promise
*append-only / streamable […] bounded memory on unbounded input*, and three of
the five issues are places this library does not deliver that. One issue
(#87) is unrelated and is what makes the release a minor.

Measured at `0.6.0`, 64-byte payloads, `tracemalloc` peak:

| Path | Now | After |
| --- | --- | --- |
| Write capture-sourced, 100k records | 0.1 MB | unchanged ✅ |
| Write **derived** (spans), 100k records | **13.7 MB** | ~0.1 MB (#96) |
| `open()` binary, 100k records | 4.9 MB | ~4.9 MB (structure is the design) |
| `open()` derived, 100k records | 20.1 MB | ~5 MB (#96) |
| `open()` JSONL, 50k records | 19.2 MB | unchanged — documented instead (#98) |
| `open()` CPU | — | ~30% faster with `check=False` (#97) |

**What is not in scope.** The reader's index is *meant* to be eager in
structure — it is what buys independent per-session iterators and O(1)
random access, and `ranges`/`layers` are documented caches. Making
`zpf.open` streaming is not on the table; #98 instead makes the guide say
what it actually is, and points at `BlockReader`/`JsonlReader` for callers
who need bounded memory. Nor is the JSONL face's eagerness a bug: a text
stream cannot be seeked back to a block.

## The issues

| Issue | What it is | Risk | Why this release |
| --- | --- | --- | --- |
| [#96](https://github.com/adamkjonsson/python-zipline/issues/96) | Coverage ledgers keep one interval per span, never coalesced | **Low** — behaviour-preserving | The writer's streaming break; biggest win per unit of risk |
| [#93](https://github.com/adamkjonsson/python-zipline/issues/93) | `SessionReader.layer()` materialises a whole participant; 3–4 parse passes per input | Low / **Medium** | The memory fault is a bug; the pass removal is not |
| [#97](https://github.com/adamkjonsson/python-zipline/issues/97) | No way to open without the checker (~30% of the pass) | Medium — new API | Needs the minor |
| [#87](https://github.com/adamkjonsson/python-zipline/issues/87) | Derive `ts_first` in `DecodeStage.record` | Low, but **observable** | **The reason this is a minor** |
| [#98](https://github.com/adamkjonsson/python-zipline/issues/98) | The reading guide promises flat memory | None — docs | Independent; patch-safe |

## Phase 1 — #96: coalesce the coverage ledgers

The release's centre, and the one to land first: it changes no verdict, and
every later phase measures against it.

- [ ] `coalesce(intervals)` in [`_intervals.py`](../src/zpf/_intervals.py),
      which is already the single home for this arithmetic. Property-test it
      against the naive `sorted()` of the unmerged list — `complement` and
      `intersections` must agree on both.
- [ ] `_StreamLedger.spans`/`.undecoded` ([`conformance.py:222`](../src/zpf/conformance.py))
      become sorted disjoint sets, merged on insert. Keep an explicit flag for
      *some record cited this stream*, which `findings()` gates the interior-gap
      check on — coalescing cannot tell an empty list from a merged-away one.
- [ ] The stages' `_Ledger._cited`/`_marked` ([`decode.py:202`](../src/zpf/decode.py))
      the same way. **The one asymmetry to preserve**: `autofill` needs
      `intersections(cited, marked)` to catch a range both cited and explicitly
      marked. Coalescing each list *separately* preserves it exactly; coalescing
      them together would destroy it.
- [ ] Drop the now-redundant `sorted()` calls at `covered` and in `autofill`.
- [ ] **Acceptance, measured**: writing 100k derived records peaks at the
      capture-sourced 0.1 MB, and 100k records citing one identical range holds
      one interval (7.3 MB → ~0). Keep the measurement script in the repo —
      a regression here is invisible to the suite otherwise.
- [ ] `KNOWN_PASSING` stays full and no vector's verdict moves. If one does,
      stop: the coalescing is wrong, not the vector.

## Phase 2 — #93: the reader's passes

Two halves, deliberately separated because only one is safe.

- [ ] **The memory fault** ([`reader.py:319`](../src/zpf/reader.py)):
      `stream_layer(list(self.stream(pid)), ...)` materialises every record of
      a participant to keep one answer. `stream_layer` iterates its argument
      once, so widening the parameter from `Sequence` to `Iterable` and passing
      the generator fixes it outright — same eager semantics, same error
      timing, O(1) memory. `zpf.stream_layer` is public, so the widened type is
      a changelog *Changed* line; widening an input type breaks no caller.
      **This half is patch-safe** and could ride the `0.6.1` with #98.
- [ ] **The extent pass** ([`decode.py:306`](../src/zpf/decode.py)):
      `_extent_and_gaps` re-reads each input stream at the first Session End.
      The indexing pass already visits every block, so a running per-participant
      extent in `_SessionIndex` removes the pass. **The wrinkle**: the extent
      model differs by layer (hole-inclusive for stream-oriented, cumulative
      payload for packet-oriented), and the layer is not known while indexing —
      so accumulate both and choose once it resolves. Verify against
      `check_coverage`, which must keep measuring identically.
- [ ] **Do not** take the issue's third option (resolve the layer from the first
      record carrying a `decoder_id`, validate the rest lazily) without a
      decision recorded here: it moves when a mixed-layer participant raises,
      from `layer()` to mid-iteration, and both the checker and `strict`
      reading lean on that timing. The conservative fix above gets the memory
      without touching it.
- [ ] Correct the issue's arithmetic in passing: pass 2 fires **only** for an
      `adjacency = units` participant, because `is_unit_sequence` short-circuits
      on the byte before consulting the layer
      ([`reassembly.py:563`](../src/zpf/reassembly.py)). The measured 4.00× is
      real but specific to the field-granular input it was measured on; an
      ordinary transport input pays 3.

## Phase 3 — #97: `check=` on the reader

- [ ] `zpf.open(..., check=True)` / `FileReader(check=…)`; `False` skips the
      per-block `_admit` call and the end-of-stream `finish()`.
- [ ] `strict=True, check=False` raises `ValueError` — strict mode's entire
      content is *raise on what the checker found*.
- [ ] `_check_self_derivation` stays on regardless: it is a path comparison on
      the Source table, costs nothing per block, and is the one rule whose
      violation makes spans resolve against the wrong file.
- [ ] Structural diagnostics (truncation, trailing bytes) still arrive — they
      come from `BlockReader`/`JsonlReader`, not the checker. Test that, and
      test that `diagnostics`/`unplaceable` carry no `"nonconformant"` entries
      with the checker off.
- [ ] Docs: the option in the reading guide and in
      [robustness](../docs/user/howto/robustness.md), each saying what is given
      up. The honest framing is *for a file this process just wrote*, not
      *for speed*.

## Phase 4 — #87: derive `ts_first` in `decode_stage`

- [ ] Mirror [`sessionize.py:237-241`](../src/zpf/sessionize.py) into
      `DecodeStage.record` ([`decode.py:530`](../src/zpf/decode.py)): when both
      `ts` and `ts_first` are omitted, derive `ts_first` with `_derive_ts_first`
      and write it only when earlier than the derived `ts`. The helper and
      `StreamView.ts_first_for` already exist; it is about four lines.
- [ ] A `ts_first` passed explicitly is still written as given, and a record
      citing no single range still has nothing to derive from.
- [ ] Changelog **Changed**, not Added: existing `decode_stage` callers start
      writing an option they did not. Update the `ts_first` docstring, which
      currently states the opposite ("Written as given and never derived here").
- [ ] **Heads-up to kober before the tag.** Its fixtures gain the option on
      every unit drawn from more than one input record — a message reassembled
      from several TCP records, a TLS record split across segments. This is the
      review it was deferred out of `0.6.0` to protect, so it gets the warning
      rather than the surprise.

## The risk this plan carries

The same one the `0.6.0` plan carried, and it is worth naming rather than
discovering: **[zipline#166](https://github.com/adamkjonsson/zipline/issues/166)
is open and `spec`-labelled.** A fragmented datagram over a `units` input has
no conformant record, because `0.22`'s permission is keyed on `seq_start`; the
preferred option extends that permission to fragment reassembly, which lands in
`_check_cites` in [`sessionize.py`](../src/zpf/sessionize.py) — the stage
`0.6.0` shipped. If that becomes `0.24`, it arrives as a port and swallows this
release the way `0.22`/`0.23` reshaped the `0.6.0` plan.

**Do not wait for it.** Every issue here is independent of the spec, four of
the five are small, and holding finished work behind an unanswered spec
question is the mistake #77 nearly made. If `0.24` is cut mid-flight, the port
becomes Phase 0 of a replan and these phases renumber behind it — which is
exactly what the `0.6.0` plan did, and it survived the move.
