# Migration plan: `python-zipline` 0.9 → 0.12

Target: [Zipline Payload Format 0.12](https://github.com/adamkjonsson/zipline/blob/v0.12/docs/zipline-payload-format.md)
(tag `v0.12`). Current: 0.9.

## What we are actually migrating to

Three spec releases separate us from the target, but only one of them contains
breaking changes:

| Release | Nature | Work for us |
|---------|--------|-------------|
| `0.10` | **Breaking.** Removes a JSONL key, renames a value, replaces the file-kind discriminator, adds two options, adds the JSONL escapes | Essentially all of it |
| `0.11` | Corrective. Six fixes to `0.10`, no new surface | One new `sequenced_basis` value (`trivial`) |
| `0.12` | Corrective. Three fixes to `0.11`, no new surface | Pins the merge tie-break — **we already do it** |

So this is a **0.9 → 0.10 port plus two rounds of clarification**, and the
clarifications mostly tell us we were already right. The version we stamp is
`0`/`12`; everything else derives from `0.10`.

There is still **no version-upgrade transform** — it was floated for `0.12` and
deferred again. `0.9` files stay disposable.

---

## Strategic decisions

Two need a call before work starts; the rest are recommendations I'd proceed on.

### D1 — Drop 0.9 support entirely — **DECIDED: yes**

`python-zipline` becomes a **single-version library implementing 0.12 only**.
No dual path, no compatibility flag, no read-only 0.9 reader.

Consequences, now settled rather than open:

- Any `.zpf` this library has already written is unreadable by it after the
  port, and there is no transcode path in 0.12. Files that still matter must be
  regenerated from their original captures.
- A 0.9 file now fails at the version gate as **structural corruption**
  (`version_major = 1` is a major we do not implement), which is the correct
  and loud failure — not a silent misparse.
- Every 0.9-specific assertion in the test suite **flips** rather than gaining a
  variant. See [the test surface](#the-test-suite-is-part-of-the-surface) below.
- The `zipline_version_update` branch's 0.9 relabelling work (commit `061812c`)
  gets superseded in Phase 7 — the prose it added about "the standard means 0.9"
  becomes wrong on merge, and is already flagged there.

### D2 — Implement the filter/reorder transform now — **DECIDED: defer**

`0.10` permits a decoded-layer filter or reordering stage (it is a decode stage,
inheriting `decoder_id`s and marking dropped regions `skipped`). We will not add
one during this port.

We must still **read** such files correctly — the `reordered-decoded` vector is
`accept` tier and Phase 6 covers it. Only the ability to *write* one is deferred.
Worth a tracking note so it is a conscious gap rather than an oversight.

### D3 — Branch and versioning *(proceeding unless you object)*

Work on a new branch off `zipline_version_update`. Keep `__version__`
(currently `0.1.0`) independent of the spec version — they already are, and
coupling them would imply a compatibility promise the package does not make.
Record the implemented spec version as a separate constant, e.g.
`zpf.SPEC_VERSION = (0, 12)`, so it is introspectable rather than buried in
`FileHeader` defaults.

## Acceptance criteria: the 26 conformance vectors

This is the single most important structural decision in the plan, so it comes
before the phases.

`v0.12` ships 26 hand-built vectors with a `manifest.json` declaring each one's
tier and expected outcome. They are built from the normative text rather than
generated by any implementation, which is exactly what makes them able to catch
us diverging.

| Tier | Count | Contract |
|------|-------|----------|
| `accept` | 16 | Parse cleanly; the `.jsonl` file is the expected projection |
| `isolate` | 5 | Well-framed, semantically invalid: discard the smallest sound unit, report a diagnostic, do not reject outright |
| `reject` | 5 | Structural corruption: refuse the file |

**Vendor them into `tests/vectors/` and wire them into pytest as Phase 0**,
before touching `src/`. Every phase below then has an objective, externally
defined completion signal, and the count of passing vectors becomes the progress
metric. Without this we would be grading our own homework — which is how the
`time_units` bug survived in the first place.

Two vectors deserve specific mention:

- **`chain/`** (3 files, 1648 bytes) is the only fixture exercising two-hop
  resolution through a decoded-layer pass-through, the recovery walk, and digest
  verification together. It is the acceptance test for Phase 5, our highest-risk
  phase, and the only place the coverage guarantee is genuinely checkable.
- **`raw-minimal`** is byte-for-byte the spec's worked example — which is what
  [tests/test_golden.py](tests/test_golden.py) currently hand-maintains as an
  inline hex blob. Vendoring the vector lets that blob be deleted rather than
  re-derived for the new version stamp.

## Phased plan

Ordered by dependency. Each phase should land green before the next starts.

### Phase 0 — Vector harness *(no `src/` changes)* — **DONE**

Vendored `vectors/` from `v0.12` into `tests/vectors/` (26 directories, 76
files, provenance in `tests/vectors/VENDORED.md`), with a manifest-driven
harness in `tests/test_vectors.py` parametrised over the three tiers. Multi-file
vectors expand to one case per `.zpf`, so `chain` yields three: **28 cases** in
total.

**Baseline: 1 of 28 passing.** The suite stays green throughout the migration
via a ratchet — a case is a hard requirement only once its name is in
`KNOWN_PASSING`; everything else is `xfail(strict=False)`, so newly-working
vectors surface as `XPASS` and are then promoted. `KNOWN_PASSING` only grows.

Three findings, all of which justified the phase:

- **Four vectors appeared to pass; only one did.** `reject-length-misaligned`,
  `reject-payload-len-overrun` and `reject-unknown-minor` were all being refused
  with *"unsupported version_major 0"* — the version gate firing long before the
  check each vector actually exercises. The harness now asserts what each
  `reject` vector is refused **for** (`_REJECT_REASONS`), which demoted them to
  honest failures. Only `reject-bad-magic` passes for its own reason.
- **`reject-unknown-major` is a 0.9 file** — it stamps `version_major = 1`,
  `version_minor = 0`. Our reader accepts it, correctly, because that is our
  version. It is [D1](#d1--drop-09-support-entirely--decided-yes) made concrete:
  the files this library writes today are precisely what 0.12 requires a reader
  to reject, and after Phase 1 this vector passes because we have stopped being
  a 0.9 reader.
- **The upstream vectors README contradicts the spec on the `isolate` tier** —
  its tier table says a reader MAY reject *or* isolate (matching the spec's
  semantic-violation tier), but its prose says rejecting is "as wrong as"
  accepting silently. Our harness follows the specification and accepts either,
  asserting only that the violation is not passed **silently**. Worth reporting
  upstream.

*Verification:* `429 passed, 27 xfailed`; `ruff check` clean; no `src/` change.

### Phase 1 — Version and header

Stamp `version_major = 0`, `version_minor = 12`. Accept `0`/`12`; reject any
unimplemented major **and** — while major is 0 — any unimplemented minor, as
structural corruption.

*Files:* [blocks.py:456-457, 480, 510](src/zpf/blocks.py#L456),
[jsonl.py:904](src/zpf/jsonl.py#L904).
*Unlocks:* `reject-unknown-major`, `reject-unknown-minor`; every `accept` vector
becomes parseable.
*Note:* `_parse_format` already parses componentwise and `_format_string`
already renders `0.12` correctly — no change needed there.

### Phase 2 — JSONL projection

The broad mechanical sweep, and the one that fixes live data loss.

- `time_units` → **`tick_hz`**, carrying a number. Delete the
  `_HZ_TO_TIME_UNIT` label mapping — writing `"us"` was non-conformant against
  0.9 too.
- `endpoint` always an array, including single occurrences.
- **The four escapes:** unknown block type as `{"type":"0x0042","content":…}`
  (replacing our `{"type":"unknown","block_type":…}`); unknown enum value as its
  raw number (we currently *raise* on unknown `kind`/`tcp_role`); unknown flag
  bit as a hex token (we currently *drop* it). Unknown option ids already
  round-trip correctly.

*Files:* [jsonl.py](src/zpf/jsonl.py) — 146-176, 311, 361-364, 388-390, 462-470,
492, 517, 573, 606.
*Unlocks:* all four `escape-*` vectors, `raw-minimal`, `passthrough-transport`.
*Note:* our handling of unknown JSON keys (drop + report) is already conformant.

### Phase 3 — Vocabulary and new options

- Undecoded `reason`: `tcp-gap` → **`gap`**. Real code change, not just docs —
  [decode.py:562](src/zpf/decode.py#L562) emits it.
- New option **`reason_class`** (`0x00A1`, `hole`/`bytes`), required with a
  non-canonical `reason`, and MUST agree if present with a canonical one.
- New option **`sequenced_basis`** (`0x0053`, Session), values
  `clock`/`protocol`/`external`/`trivial`.
- `skipped` becomes canonical — we already emit it, so this is documentation.

*Files:* `_frame.py` (ids), [blocks.py](src/zpf/blocks.py) (Undecoded, Session),
[writer.py](src/zpf/writer.py) (`undecoded()`, `begin_session()`),
[jsonl.py](src/zpf/jsonl.py) (mapping).
*Unlocks:* `undecoded-skipped`, `undecoded-reason-class`, `sequenced-basis`.

### Phase 4 — Ordering semantics

Mostly deletion, which is the pleasant surprise of this migration.

- **Remove** both timestamp rejections: the merge's hint-less backwards-time
  check ([order.py:114](src/zpf/order.py#L114)) and the same check in
  `verify_sequenced` ([order.py:258](src/zpf/order.py#L258)). Timestamps are not
  an ordering invariant; a reader must not reject or re-sort on them.
- **Confirm** the merge tie-break is `(timestamp, participant_id)` and that the
  merge is stable with respect to stored order. [order.py:204](src/zpf/order.py#L204)
  already does this — 0.12 ratified our behaviour, so this is a test, not a change.
- Implement **hint-less** as defined: *no record in the session carries
  `seq_start` or `ack`*; one hint anywhere means not hint-less. Defer the
  `sequenced_basis` requirement to Session End / end-of-stream — one boolean per
  open session.

*Files:* [order.py](src/zpf/order.py), [conformance.py](src/zpf/conformance.py).
*Unlocks:* `hintless-merge-backwards-ts`, `merge-timestamp-tie`,
`partially-hinted-sequenced`, `isolate-sequenced-no-basis`.

### Phase 5 — The file-kind model *(the hard one)*

The only phase requiring design rather than translation.

- Re-seat file-kind inference on **`spans` versus `origin`**, not `decoder_id`.
  Today [conformance.py:280](src/zpf/conformance.py#L280) locks the file to
  "decode stage" the moment a record carries a `decoder_id`, which now rejects
  exactly the decoded-layer pass-through the spec added an example for.
- Permit Decoder Descriptors and Undecoded blocks in a **pass-through preserving
  a decoded layer**.
- Implement the **grandparent-Source rule**: such a pass-through declares the
  file its inherited Undecoded blocks name, and those blocks' `source_id` must
  resolve to it. Our `_require_source` model has no concept of this.
- Distinguish **immediate inputs** (Sources named by `origin`/`spans`) from
  Sources declared only so an inherited reference resolves.
- Unknown Source `kind` becomes an **isolatable** semantic condition — discard
  that Source and its dependents and report, rather than raising.

*Files:* [conformance.py](src/zpf/conformance.py) (substantial),
[reader.py](src/zpf/reader.py), [transform.py](src/zpf/transform.py).
*Unlocks:* `annotator-decoded`, `isolate-unknown-source-kind`, `chain`.

### Phase 6 — Decoded offset spaces

The one place 0.12 requires structure we have no equivalent of.

A decoded stream's offset space is the concatenation of that participant's
decoded record payloads in stored order — **not** hole-inclusive, unlike a
transport stream's. A decoded record's own range is positional:
`[Σ payload_len of preceding records, + its own)`.

Free for forward reading (one running counter per participant); O(k) for random
access, which the spec now says explicitly and recommends solving with
per-participant prefix sums built on a first pass. Decide where those live —
probably alongside the existing session state in `reader.py` rather than in a new
index type.

*Files:* [decode.py](src/zpf/decode.py), [reassembly.py](src/zpf/reassembly.py),
[transform.py](src/zpf/transform.py) (`check_coverage`).
*Unlocks:* `reordered-decoded`; completes `chain` coverage verification.

### Phase 7 — Surface and documentation

- `zpf.SPEC_VERSION`, docstrings, `CLAUDE.md`, `README.md`, `docs/`.
- Revisit `CLAUDE.md`'s current instruction that "the standard means 0.9" and the
  0.10-avoidance note — both become wrong on merge.
- Delete the hand-maintained hex blob in `test_golden.py`, superseded by
  `raw-minimal`.
- Sphinx build clean under `-W`; `ruff check` clean.

## Effort and risk

Phases 0–4 are well-understood: a vector harness, one broad but mechanical JSONL
sweep, two new options, one rename, and a net deletion in `order.py`. I would
expect these to land steadily and to move the vector count most of the way.

Phase 5 is where the real work and the real risk sit. It is not a large diff by
line count, but it changes the model the checker is built on, and the checker is
what the writer relies on to make non-conformant files hard to write. `chain/`
is the thing that will tell us whether we got it right.

Phase 6 needs a short design pass before it can be estimated honestly — the
question is where prefix sums live and who owns them, not whether the rule is
understood.

**Biggest risk:** treating Phase 5 as a patch rather than a re-seating, and
ending up with a checker that passes the vectors while still carrying
`decoder_id`-shaped assumptions elsewhere (`reader.py`'s notion of a decoded
file, `transform.py`'s coverage checker). Mitigation: do Phase 5 as a deliberate
rewrite of the kind-inference, with the vectors as the contract.

### The test suite is part of the surface

Because of [D1](#d1--drop-09-support-entirely--decided-yes), the existing 426
tests do not gain 0.12 variants — their 0.9 assertions **flip**. The surface is
contained and concentrated, but it is real, and each phase must carry its own
test updates rather than leaving them to the end:

| Assertion | Occurrences | Files | Phase |
|-----------|-------------|-------|-------|
| `"zipline-payload/1"` | 7 | `test_jsonl.py` | 1 |
| `time_units` | 10 | `test_jsonl.py` | 2 |
| `tcp-gap` | 6 | `test_transform.py`, `test_jsonl.py`, `test_decode.py` | 3 |
| `version_major` gates | — | `test_blocks.py`, `test_binary.py`, `test_golden.py` | 1 |
| `{"type":"unknown"}` projection | — | `test_jsonl.py` | 2 |

`test_golden.py`'s inline hex blob is deleted outright in Phase 7, superseded by
the `raw-minimal` vector. Note that `UnknownBlock.block_type` (the binary-side
attribute, in five test files) is **unchanged** — only its JSONL projection
moves, so those tests stay as they are.

A useful invariant while porting: the vector count should rise monotonically and
the existing suite should stay green at the end of each phase. If a phase makes
vectors pass while breaking unrelated tests, the change reached further than
intended.

## What is already correct

Worth stating so none of it gets "fixed":

- **Componentwise version parsing** — `_parse_format` already splits and parses
  each component; we never had the float bug that sorts `0.10` below `0.9`.
- **Merge tie-break** — already `(timestamp, participant_id)`; 0.12 ratified it,
  citing that an implementation had already adopted it to make the merge testable.
- **Stable merge** — already a k-way interleave over per-participant streams that
  never reorders within a stream.
- **Unknown option ids** — already round-trip through the generic `options` array.
- **Unknown JSON keys** — already dropped with a report, as required.
- **`skipped`** — already emitted; 0.10 merely canonicalised it.
- **Packed layouts** — `spans` (28 bytes), `origin` (12), Record body (28), and
  the 2340-entry per-option cap are unchanged from 0.9 and already correct.

## Open questions

D1 and D2 are settled above. Two minor ones remain, neither blocking:

1. **Vectors checked in, or fetched at test time by tag?** This gates Phase 0.
   Checked in is reproducible, offline-friendly, and reviewable in the diff;
   fetching keeps them authoritative but makes the suite network-dependent and
   the CI flaky. **Proceeding with: checked in under `tests/vectors/`, with the
   source tag (`v0.12`) recorded in a README beside them** — unless you say
   otherwise.
2. **Is `zpf.SPEC_VERSION` worth exposing publicly**, or is the `FileHeader`
   default sufficient? Cosmetic; I lean towards exposing it, since "which
   version does this library implement" is a reasonable question to ask
   programmatically once the answer stops being "the only one there is".

## Status note

This project reviewed `0.10` and `0.11` upstream, and both reviews have been
fully absorbed: `0.12`'s changelog states it "fixes what the review of `0.11`
found", and all three of that review's findings were adopted — the merge
tie-break verbatim, including the observation that an implementation had already
converged on `(timestamp, participant_id)`. That is why several items in this
plan are ratifications of existing behaviour rather than changes. Nothing
further is owed upstream, and the review documents themselves have been removed
as superseded.
